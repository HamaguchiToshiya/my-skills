## 提案1（中）: form-implementation「バリデーション方針」に送信時のフォーカス管理を追記

- **出典（相互裏取り・UX専門媒体）**:
  - 72Technologies「Form Validation UX: When to Show Errors (2026 Guide)」 https://www.72technologies.com/blog/form-validation-ux-when-to-show-errors （送信時は全項目検証し最初のエラーへフォーカス）
  - Static Forms「Effective Form Error Messages: UX & Accessibility Guide」 https://www.staticforms.dev/blog/form-error-messages （色だけに頼らず aria 結線＋インライン直下配置）
  - UXPin「Best Practices for Error Feedback on Mobile Forms」 https://www.uxpin.com/studio/blog/error-feedback-best-practices-mobile-forms/ （仮想キーボードで隠れないよう自動スクロール／16px／44px）
- **重要度**: 中（アクセシビリティ上の欠落を補う注意書きの追加）
- **変更理由**: 現行の「バリデーション方針」は blur/送信時のエラー表示・aria-describedby/aria-invalid の結線までは記載しているが、**送信時にどのフィールドへフォーカスを戻すか**（フォーカス管理）に触れていない。キーボード/スクリーンリーダー利用者は、送信してエラーになった際に最初の問題箇所へ自動で移動しないと、どこを直せばよいか分からず離脱の原因になる。スマホでは仮想キーボードにメッセージが隠れる問題もあり、該当欄への自動スクロール＝フォーカス移動で解決する。3つの独立したUX媒体で相互に裏取りできており、WCAG 3.3.1（エラーの特定）とも整合する確立した実務パターン。
- **現行記述の該当箇所**: `skills/form-implementation/SKILL.md` 「バリデーション方針」セクション、`aria-describedby`/`aria-invalid` のバレット（編集前 32行目）の直後に1バレット追加。
- **diff**:
  ```diff
   - エラーメッセージは該当の入力欄と `aria-describedby` で関連付け、`aria-invalid="true"` を該当項目に付与する
  + - 送信時にエラーが残っている場合は、**最初のエラー項目へフォーカスを移動**する。キーボード/スクリーンリーダー利用者が最初の問題箇所に確実にたどり着け、スマホでは仮想キーボードで該当欄が隠れないよう自動スクロールされる。エラーメッセージは該当入力欄の直下にインライン配置し、視線移動を最小にする
  ```
- **影響範囲**: フォーカス移動＝a11y改善であり、`coding-standard` の a11y ルール・`pre-delivery-checklist`（フォーム送信確認）と矛盾しない。既存の「blur/送信時にエラー表示」「一度出たら input で再チェック」の記述とも独立して両立する。他 Skill への破壊的影響なし。
