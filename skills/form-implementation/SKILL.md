# フォーム実装ルール

Web制作の実案件で、フォームを実装する際は以下のルールに従う。`coding-standard` と併用する。

## 0. 着手前に確認すること（送信先・構成）

フロント側だけ作っても送信先がなければフォームは動かない。まずCLAUDE.mdの「プロジェクト概要 > フォーム」欄を確認し、記載がなければ着手前に以下を確認する。

- **送信先の仕組み**: 静的サイトならフォーム送信サービス（SSGform、Formrun等）か自前のPHP/サーバーレスか。WordPressならプラグイン（Contact Form 7、MW WP Form等）か、テーマ内実装か。未確認の場合は「フロントのマークアップ + バリデーションのみ先行実装し、送信先は仮のendpointにする」旨を明示して進める
- **確認画面の要否**: 日本の実案件では「入力 → 確認 → 完了」の3画面構成が求められることが多い。確認画面が必要か、入力画面から直接送信でよいかを確認する。判断の目安: **BtoB・入力項目が多い・クライアントの慣習がある → 確認画面あり / LP・入力3項目程度の簡易フォーム → 直接送信＋完了表示で可**。迷ったらクライアントに確認する（実装方法は後述「確認画面付き構成の実装指針」）
- **完了後の挙動**: 完了ページへ遷移（サンクスページ。広告計測でURLが必要な場合はこちら）か、同一ページ内メッセージ表示か
- **プライバシーポリシー同意**: 個人情報を取得するフォームでは「プライバシーポリシーに同意する」チェックボックス（`required` + ポリシーページへのリンク）の設置が日本の実案件では標準。**ポリシーページ自体が存在するかも確認**し、なければ用意が必要な旨をクライアントに伝える
- **送信の計測**: フォーム送信をコンバージョン計測する案件では、送信成功時のイベント送信（dataLayer push）を `analytics-setup` スキルの実装に合わせて組み込む

## マークアップの基本

- 各入力には対応する `label` を必ず設置する（`coding-standard`のa11yルールに準拠）
- 入力の種類に応じて `type` を正しく使う（`email`, `tel`, `number`, `url`等）。スマホでの最適なキーボード表示にもつながる
- 必須項目は `required` 属性 + 見た目で「必須」と分かる表示（テキストまたはバッジ）の両方を用意する。アイコンや色のみに頼らない
- `autocomplete` 属性を適切に設定する（例: 氏名は`name`、メールは`email`、電話は`tel`）。ユーザーの入力の手間を減らす
- `textarea` は高さ固定にせず、入力量に合わせて伸ばす: `@supports (field-sizing: content) { textarea { field-sizing: content; min-height: 6lh; max-height: 20lh; } }`（Chrome/Edge 123+・Firefox 152+・Safari 26.2+。Baseline 2026-06 Newly available〔2026-08-26 確認〕。未対応環境は `rows` 指定の通常のtextareaとして動くのでJSの自動リサイズは実装しない）。長文入力時にtextarea内スクロールで見返しにくくなるのを防ぐ。`min-height` は `rows` 相当の初期高さ、`max-height` はページが際限なく伸びないための上限

- **`select` の見た目がデザインに合わないときは、JSのカスタムセレクトを作る前に `appearance: base-select` を検討する**（Chrome/Edge 135+・Safari 27+ で主要2エンジンが揃った）。ネイティブのキーボード操作・モバイルのピッカー・フォーム送信がそのまま残るので、a11y の作り込みが要らない。**未対応環境ではネイティブの見た目に戻るだけ**なので進行的強化として書ける。採用順序と実装形は `js-implementation-standard` の「セレクトボックス」を参照

  ```scss
  select { appearance: base-select; /* 以下、::picker(select) / ::picker-icon / ::checkmark を装飾 */ }
  ```

## 入力欄の状態スタイル（惜しいフォームが落ちる5つの穴）

入力欄・ボタンの状態スタイルは以下を必ず守る（フォーカスリングと状態スタイルの不足は `design-verification` の検証ゲート **#29・#30** で検出される。下記5点は #30「入力の5点」として design-checker が検出し、`form-validator` も本スキルを基準に観点1（HTML/CSS側）でレビューする）。

- **状態間で `border-width` を変えない**: default / hover / focus / error のすべてで 1px を維持する。フォーカスやエラーで枠を太らせるとレイアウトが1pxずれる。状態変化は `border-color` / `background-color` / `outline` / `box-shadow` で表現する
- **フォーカスリングは `border` でなく `outline` で作る**: `outline: 2px solid〈フォーカス色〉; outline-offset: 1px` を基本形にする。リングに `transition` を掛けない（キーボード利用者への即時表示が必須）
- **入力欄と送信ボタンの高さを揃える**: 同一フォーム内は基準の高さ（44px以上。タップターゲットの下限を兼ねる）を共有する。「38pxの入力欄＋44pxのボタン」の不揃いが最頻出の作り込み漏れ
- **エラーメッセージのスロットは常時確保する**: エラー文の表示領域に `min-height: 1lh` を確保し、エラー出現時にページ全体が押し下がるレイアウトシフトを防ぐ
- **disabled は3チャネルで表現する**: `disabled` 属性（または `aria-disabled="true"`）＋ `opacity`（0.5前後）＋ `cursor: not-allowed` の3点セット。opacityだけの非活性表現は「押せないのか壊れているのか」が伝わらない（「送信時の状態管理」の送信中非活性と共通）

上の5点（#30「入力の5点」）とは別枠で、次も必ず守る:

- **入力欄の `font-size` は 16px 以上にする**: iOS Safari は 16px 未満の入力欄にフォーカスすると自動でページをズームし、崩れて見える原因になる。デザインで小さく見せたい場合も入力欄本体は `1rem` 以上を維持し、見た目は `padding` や高さで調整する

## バリデーション方針

- **まずネイティブバリデーション（`required`, `pattern`, `type`, `minlength`/`maxlength`）を優先**する。ブラウザ標準の仕組みで足りる場合はJSを増やさない
- JSでのリアルタイムバリデーションが必要な場合（送信前に細かくフィードバックしたい等）は以下を基本にする:
  - 入力中（`input`イベント）ではなく、**フォーカスが外れた時（`blur`）または送信時**にエラーを表示する（入力中に赤くなるとユーザーが不安になりやすい）
  - 一度エラーが出た項目は、その後 `input`イベントでリアルタイムに再チェックし、直ったら即座にエラー表示を消す
- エラーメッセージは具体的に書く（「入力してください」ではなく「メールアドレスの形式で入力してください」）
- エラーメッセージは該当の入力欄と `aria-describedby` で関連付け、`aria-invalid="true"` を該当項目に付与する
- 送信時にエラーが残っている場合は、**最初のエラー項目へフォーカスを移動**する。キーボード/スクリーンリーダー利用者が最初の問題箇所に確実にたどり着け、スマホでは仮想キーボードで該当欄が隠れないよう自動スクロールされる。エラーメッセージは該当入力欄の直下にインライン配置し、視線移動を最小にする

## 送信時の状態管理

- 送信ボタンは、送信中は非活性化 + ローディング表示にし、二重送信を防ぐ
- 送信成功/失敗をユーザーに明示する（成功時は完了画面またはメッセージ表示、失敗時は理由とリトライ手段を示す）
- 非同期送信（fetch等）の場合、通信エラー時のフォールバック文言（「時間をおいて再度お試しください」等）を用意する

## セキュリティ・スパム対策

対策は軽量なものから段階的に。いきなりreCAPTCHAを入れず、まずhoneypot＋サーバー側検証で様子を見る判断もあってよい。

### honeypot（第一段階・実装コストほぼゼロ）

```html
<!-- botだけが入力する罠フィールド。CSSで視覚的に隠す（display:noneはbotに見抜かれることがあるため画面外へ） -->
<div class="c-form__hp" aria-hidden="true">
  <input type="text" name="company_url" tabindex="-1" autocomplete="off">
</div>
```

```scss
.c-form__hp {
  position: absolute;
  left: -9999px; // 画面外に飛ばす
}
```

サーバー側でこのフィールドに値が入っていたらbotと判定して送信を拒否する。

### reCAPTCHA v3（第二段階・要APIキー）

- 案件要件とAPIキー準備の有無をユーザーに確認してから実装する
- v3はスコア判定型（ユーザー操作不要）。**フロントのトークン取得だけでは無意味**で、サーバー側でsiteverify APIを叩いてスコア検証するところまでが実装
- スコア閾値は0.5から始め、正規ユーザーの弾かれ具合を見て調整する
- バッジ表示が必須。非表示にする場合は代替のクレジット表記が規約で求められる点に注意

### サーバー側の必須検証

フロントのバリデーションは**UX向上のためのもので、セキュリティ対策ではない**（JSを無効化すれば素通りする）。サーバー側で必ず再検証する:

- 必須項目・形式チェックの再実施
- **メールヘッダインジェクション対策**: ユーザー入力（特に名前・メール欄）に改行コード（`\r` `\n`）が含まれていたら拒否する。改行を混ぜてBcc等のヘッダを注入し、スパム踏み台にする古典的攻撃
- 出力時のエスケープ: 確認画面・完了画面・自動返信メールに入力値を表示する際は `htmlspecialchars()` を通す（XSS対策）
- **CSRF対策**: 自前PHPで実装する場合はCSRFトークンを入れる（セッションでトークンを発行 → hiddenフィールドで送信 → 送信時に照合。不一致なら拒否）。WordPressは `wp_nonce_field()` / `wp_verify_nonce()`（`wordpress-development` 参照）、Contact Form 7等のプラグインは内蔵済み

## 確認画面付き構成（入力 → 確認 → 完了）の実装指針

確認画面ありの場合の要点。自前PHP実装で崩れやすいポイントに絞る。

- **値の受け渡しはセッション推奨**: 入力画面POST → セッションに保存 → 確認画面で表示（`htmlspecialchars()` 必須）→ 送信。hiddenフィールドで引き回す方式でもよいが、その場合は**確認 → 送信時にサーバー側で全項目を再バリデーション**する（hiddenは開発者ツールで改ざんできるため。セッション方式でも送信時の再検証が原則）
- **CSRFトークン**は入力画面の表示時に発行し、送信（最終POST)時に照合する（上記セキュリティ節参照）
- **「戻る」対応**: 確認画面から入力画面に戻ったとき、セッションの値で入力欄を復元する（消えると離脱の原因になる）
- **二重送信対策**: 送信完了時にセッションのトークンを破棄し、リロードによる再送信を拒否する（完了ページへのリダイレクト＝PRGパターンも併用）
- 確認画面はJSでのモーダル表示でも代用できる（画面遷移なし）。その場合も送信は1回のPOSTで、サーバー側検証の要件は同じ

## フォーム送信サービスを使う場合（SSGform等・静的サイトの第一候補）

静的サイトでサーバーサイドを書かずに済ませる標準構成。PHPが動かないホスティングでも使え、自前PHPよりメール到達性のトラブルが少ない（送信元がサービスのドメインになるため）。

1. **`action` にサービス発行のエンドポイントURLを設定**し `method="post"` で送信する（マークアップ・バリデーションは本スキルの前節どおり。`name` 属性が通知メールの項目名になるサービスが多いので日本語名の可否を確認）
   - **`name` 属性は「HTML ⇔ バリデーションJS ⇔ 送信先（サービス設定・PHPの受け取りキー）」の3者で必ず一致させる**。1箇所でも食い違うと見た目は動くのに値が届かない機能不全になる（form-validator の致命判定対象）
2. **完了後の挙動をサービス管理画面で設定**する: サンクスページへのリダイレクト先URL（コンバージョン計測をURLで拾う場合は必須。`analytics-setup` 参照）
3. **通知先・自動返信**はサービス側の設定で行う。テスト送信で通知メール受信・自動返信・迷惑メールフォルダ・サンクスページ遷移まで確認する
4. **スパム対策**はサービス側の機能（reCAPTCHA連携・独自フィルタ等）を確認して有効化する。honeypotを自前で足す場合は、未知のフィールドを受け付けるかサービスの仕様を確認してから
5. **プランの制限**（月間送信件数・広告表示・添付可否等）を確認し、商用案件ではクライアントに伝えて有料プランの要否を判断してもらう

サーバー側検証はサービスに委ねる構成のため、フロントのバリデーション＋サービス側スパム対策で成立させる。要件に合わない場合（確認画面必須・項目が特殊等）は次節の自前PHPに切り替える。

## PHPでのメール送信実装（自前実装の場合）

静的サイト＋レンタルサーバーで、プラグインや外部サービスを使わず自前のPHPで送信する場合の標準形。

送信処理（`mb_language` / honeypot / CSRF照合 / ヘッダインジェクション対策 / サーバー側の再バリデーション / `mb_send_mail`）と、入力画面側のCSRFトークン発行のコードは `references/php-mail.md` が正。自前PHPを書くときは必ずそちらを読んでから着手する。

### メール到達性の注意（不達トラブル対策）

- **Fromはサイトと同一ドメインのアドレスにする**。フォーム入力者のメールをFromに入れるのはなりすまし扱いされ不達の主因になる。入力者のアドレスは `Reply-To` に入れる
- Gmail宛の要件が年々厳しくなっているため、送信ドメインの**SPFレコード設定を確認**する（レンタルサーバー標準のメール機能を使っていれば通常は設定済み。独自構成の場合はsite-deploymentのDNS設定時に確認）
- 自動返信メール（入力者宛）を付ける場合、「返信は届かない場合がある」前提でクライアントに説明する（キャリアメールの受信拒否等）
- テストは必ず**Gmail・キャリアメール等の複数の宛先**で行い、迷惑メールフォルダも確認する

### WordPressの場合

- テーマ内に自前のmail()実装を書かず、**Contact Form 7等のプラグインを基本とする**（保守性・スパム対策の更新性のため）
- CF7のスパム対策はAkismet連携かreCAPTCHA連携（インテグレーション機能）で行う
- 送信元アドレスの原則（同一ドメインFrom）はプラグインでも同じ。CF7のメール設定で `[your-email]` をFromに入れない
- 到達性に問題がある場合はWP Mail SMTPプラグインでSMTP送信に切り替える

## coding-standardとの命名

- フォーム全体は `p-` （ページ固有）または汎用フォームなら `c-form` のようにコンポーネント化する
- クラス命名・状態クラス（`is-error` 等）のルールの正は `coding-standard`。エラー状態はstateクラスをJSで付け外しし、スタイルはSCSS側で管理する

## 出力形式

- HTML + SCSS + （必要な場合のみ）JSのバリデーション + サーバーサイド処理をまとめて実装する

対応レビューエージェント: `form-validator`
