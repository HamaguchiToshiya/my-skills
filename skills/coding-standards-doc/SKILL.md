# コーディング規約書ドキュメント化ルール

普段使っているコーディングルール（FLOCSS命名、モダンCSS方針、WordPressテーマ構成）を、クライアントや他の制作者に渡せる規約書・引き継ぎ資料としてまとめる際に使う。

## 0. 着手前に確認すること（用途）

同じ「規約書」でも用途で内容の粒度が変わるため、依頼内容から用途を判断する。曖昧な場合は簡潔に確認する。

- **社内の別担当者への引き継ぎ用** → 実装の意図・注意点まで詳しく書く
- **クライアント向けの納品資料** → 専門用語を避け、「何ができる／触ってよい範囲」を中心に書く
- **将来の自分用メモ** → 簡潔な箇条書き中心でよい

## 基本構成（引き継ぎ・社内向けの場合）

1. **概要**：使用技術スタック（HTML/SCSS、WordPress、ACF等）とサイト構成の全体像
2. **ディレクトリ構成**：フォルダツリーと役割の説明
3. **CSS設計方針**：FLOCSSの各層（`l-` `c-` `p-` `u-`）の使い分けルールと具体例
4. **採用しているモダンCSS機能**：使用機能の一覧と、対応ブラウザ範囲の考え方
5. **JS実装方針**（該当する場合）：UIコンポーネント（ドロワー・タブ・モーダル等）の実装規約とモジュール構成（出所は `js-implementation-standard`）
6. **アニメーション方針**（該当する場合）：モーショントークン（duration・easing の共通定義）・MOTION ダイヤル値（design-brief.md）と `prefers-reduced-motion` への対応方針（出所は `animation-implementation`）
7. **開発ツール**（該当する場合）：SCSSのビルド方法、Prettier/ESLint/Stylelintの設定と実行コマンド（`npm run format` 等。設定内容の出所は `code-formatting-lint`）
8. **WordPress固有のルール**（該当する場合）：テンプレート階層、ACFフィールドの命名・管理方法、カスタム投稿タイプ一覧
9. **解析・計測の設定一覧**（該当する場合）：GA4 / GTM / Search Console のアカウント・計測イベント・権限の引き継ぎ状況（転記元は `analytics-setup` の納品時引き継ぎ項目）
10. **納品物一覧**：納品ファイル・アカウント・URL・検収条件を1つの表に（検収期間等の条件は受注時に `hearing-estimate` の「検収・納品・請求」節で決めたもの）
11. **今後の追加・修正時の注意点**：新しいセクションを追加する際に守るべきルール

## クライアント向け（簡易版）の場合

- 専門用語（FLOCSS、BEM等）はそのまま使わず、「デザインの部品ごとにファイルを分けています」のように言い換える
- 「触ってよい範囲」（例: WordPress管理画面からの文章・画像差し替え）と「触ると崩れる可能性がある範囲」を明確に分ける
- スクリーンショットを使う想定がある場合は、その旨をこちらから提案する（実際の画像添付はユーザー側で行う）

## 出力形式

- 通常はMarkdownファイル（例: `docs/coding-guide.md`）
- 「Wordで納品したい」等、.docx形式が明確に求められた場合はWordドキュメントとして作成する（docx変換の専用スキルは現状無い。pandoc等の変換ツールが環境にあるかを先に確認し、無ければMarkdown納品＋Wordへの貼り付け手順の提示を提案する）
- 見出し構造を保ったまま、既存スキル（coding-standard / wordpress-development 等）の内容を転記するのではなく、その案件の実際のコードに即して要約・具体化する
