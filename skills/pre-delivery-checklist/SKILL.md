# 納品前チェックリスト（機械チェック + AI判断の2段構成）

コーディング完了後、納品・公開前の最終確認に使う。

**線引き**: 本スキルは「公開作業に入る前」のコード・コンテンツ品質チェック。公開作業と公開直後チェックは `site-deployment`、計測確認は `analytics-setup` が担当する。

## 実行手順（必ずこの順番）

### STEP 1: 機械チェック（スクリプトに任せる。自分で目視走査しない）

コードにアクセスできる環境（Claude Code / ファイル添付あり）では、まず同梱スクリプトを実行する。

```bash
node ~/.claude/skills/pre-delivery-checklist/scripts/check.mjs <対象ディレクトリ>
# エージェント処理で結果を使う場合は --json
node ~/.claude/skills/pre-delivery-checklist/scripts/check.mjs <対象ディレクトリ> --json
```

（`~` はユーザーホーム。`~/.claude/skills` のジャンクション設置が前提＝作業手順書「スキル・エージェントの置き場」。PC固有の絶対パスをここに書かない）

スクリプトが検出する項目（AIは再チェックしない。結果をそのまま採用する）:

| 分類 | 検出内容 |
|---|---|
| HTML | alt欠落 / width・height欠落 / autoplay動画のmuted・playsinline欠落 / title・meta description・OGP欠落 / noindex残り / rel="noopener"漏れ / 見出し階層飛び / h1の個数 / lang属性 / favicon / ダミーテキスト / TODOコメント |
| JS | console.log・debugger の残り（インラインscript含む） |
| PHP | var_dump・print_r の残り / WP_DEBUG true（PHPファイルにはHTMLの検査も適用。インラインscriptのデバッグコードはそちらで検出） |
| 画像 | 300KB超の重い画像 / WebP未変換の大きなJPG・PNG |

- 上記の表は概要。**正確な検出項目は check.mjs のヘッダコメント（実装と同居）を正とする。実装を変更したら必ずヘッダコメントも同時に更新する**（両者がズレていたらそれ自体をバグとして直す）
- スクリプトが実行できない環境（コードが渡されていない等）の場合のみ、上記項目を目視で確認するか、チェックリストとして提示する
- ERROR は修正必須。WARN は文脈判断（例: `img-size` はCSSで `aspect-ratio` 指定済みなら不問）。ただし**公開予定サイトの `noindex` 残骸はWARN表示でもブロック扱い**（下記「納品可否判定」）。例外はフォーム送信完了ページ（thanks.html 等、`boilerplate-pages` の規約で noindex 必須のページ）で、これは想定内としてブロック対象にしない（check.mjs はファイル名または `<!-- noindex: intended -->` マーカーで判定し INFO に格下げする）

### STEP 2: AI判断チェック（機械化できない項目のみ）

スクリプトでは判定できない、意味理解が必要な項目をレビューする。

- [ ] alt の**内容**が適切か（存在チェックはSTEP 1済。「画像」「写真」等の無意味なaltでないか、装飾画像に長文altがないか）
- [ ] リンクテキストだけで遷移先が分かるか（「こちら」だけ等になっていないか）
- [ ] title / meta description が**ページ内容に即しているか**、ページ間で使い回しになっていないか
- [ ] コントラスト比が十分か（薄いグレー文字、ボタン。WCAG AA: 通常4.5:1 / 大テキスト3:1。判定基準の正は design-taste ⇔ design-verification の数値同期表で、ここは最終関門としての再掲）
- [ ] フォーム要素の label 紐付けが**正しい対応関係**か
- [ ] 極端に長い日本語テキスト・英単語で崩れる恐れのある構造がないか
- [ ] 不要なCSS/JSの読み込みがないか
- [ ] 個人情報を扱うフォームにプライバシーポリシーと同意チェックがあるか
- [ ] クライアント素材・原稿が最新版か（判断できなければ「要人間確認」に回す）
- [ ] `example.com`・`test@` 等のダミードメイン・ダミーアドレスの残骸がないか（本文・リンク・meta・フォーム送信先。**残っていたら納品ブロック**）
- [ ] 開発URL（`localhost` / `.local` / 開発サーバーのドメイン）のハードコーディングがないか（WPテーマ側の判定基準は `wordpress-development` の本番移行注意と対）
- [ ] 内部リンク・アセット参照（`href` / `src` / `srcset`）を実在ファイル・実在ページと突き合わせ、参照切れがないか（**切れていたら納品ブロック**）
- [ ] ファーストビュー内のLCP候補画像に `loading="lazy"` が誤付与されていないか（ルールの正は `coding-standard` の画像実装）
- [ ] sitemap.xml / robots.txt が用意され、内容が公開構成と一致しているか（用意の正は `seo-meta-implementation`）
- [ ] 404ページが用意されているか（静的サイト: 404.html と .htaccess の `ErrorDocument` 指定 / WP: 404.php）。内容がサイトのデザイン・導線に合っているかも見る

### STEP 3: 人間確認リスト（AIが判定できない項目を必ず列挙して渡す）

以下は推測で「大丈夫」と言わない。未確認として明示的にリスト化して渡す。

- [ ] SP / タブレット / PC の実機・実ブラウザでの表示確認
- [ ] フォーム送信テスト（バリデーション → 完了画面 → 通知メール受信まで）
- [ ] tel: / mailto: の番号・アドレスが正しいか（クライアント情報との照合）
- [ ] ブラウザコンソールにエラー・404が出ていないか（check.mjs はブラウザを起動しないため STEP 1 では検出できない。実機・実ブラウザ確認時に開発者ツールで見る）
- [ ] SSL化・https リダイレクト（`site-deployment` の領域）
- [ ] WPの場合: パーマリンク設定 / デフォルトコンテンツ削除 / ACF同期（acf-json反映）/ 「検索エンジンを回避」設定のOFF / `WP_DEBUG` が false / フォーム送信テスト（本番のメール環境）（WP移行**後**の再確認は `site-deployment`「移行後の必須確認」と対。改訂時は両方揃える）
- [ ] SNSシェアデバッガーでのOGP表示確認

## 納品可否判定（判定の考え方はこのスキルが正。pre-delivery-checker もこの基準で判定する）

総合判定は3値で出す:

- 🟢 **納品可** / 🟡 **軽微な修正後に納品可** / 🔴 **修正必須項目あり**
- STEP 3 の手動チェックに未実施項目がある場合、🟢/🟡 でも「手動確認完了が条件」と必ず明記する（実機確認・フォーム送信テスト未了のまま無条件の「納品可」を出さない）

**🔴 納品ブロック（1件でもあれば「納品可」としない）**:

1. check.mjs の ERROR が残っている（ダミーテキスト・alt欠落・noopener漏れ・debugger 等）
2. 公開予定サイトの `noindex` 残骸（check.mjs ではWARN表示だがブロック扱い。フォーム送信完了ページ等の想定内 noindex＝check.mjs が INFO 表示にしたものは除く）
3. リンク切れ・参照切れ（内部リンク・アセット参照）
4. `example.com`・ダミー電話番号・ダミーアドレス等の残骸

判定は甘くしない。確認できなかった項目を「問題なし」に含めず、「未確認」として分けて報告する。

## 出力形式

必ず3ブロックに分けて報告する:

1. **機械チェック結果**: check.mjs の ERROR / WARN を要約（件数と主要な指摘）
2. **AIレビュー結果**: STEP 2 の指摘（ファイル・行を特定して具体的に）
3. **人間確認リスト**: STEP 3 のうち今回該当するもの

- 推測で「たぶん大丈夫」とは言わない。確認できないものは必ず「未確認」と明示する
- 何も渡されず「チェックリストが欲しい」だけの場合は、STEP 1〜3 の項目をリストとして提示してよい

対応レビューエージェント: `pre-delivery-checker`
