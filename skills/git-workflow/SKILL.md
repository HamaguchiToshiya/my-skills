# Git運用ルール

Web制作の実案件でGitを使う際のブランチ運用・コミットメッセージ規約と、初心者向けの操作説明をセットにしたルール。

## 前提：ユーザーはGit操作に不慣れ

- コマンドを提示する際は、コマンドだけでなく **「何をするコマンドか」を一言添える**（例: `git add .` ← 変更したファイルを『次の保存対象』に入れる操作）
- いきなり複数コマンドを羅列せず、今の状況で次に打つべき1〜2個に絞って案内する
- エラーが出た場合は、エラーメッセージの内容を噛み砕いて説明してから対処法を出す（英語のエラーをそのまま貼るだけにしない）
- 破壊的な操作（`git reset --hard`, `git push --force`, `git checkout .`で変更を捨てる等）を勧める前には、必ず「これをやると◯◯が消えます」と影響を説明し、了承を得る
- このテンプレートでは `.claude/settings.json` の deny 設定で `rm -rf` / `git push --force` / `git reset --hard` / `git clean` / `git filter-branch` / `git rebase` / `git commit --amend` 等を機械的にもブロックしている（CLAUDE.mdの言う「お願いではなく柵」の二重化。了承を得た上で実行する場合も deny の解除が必要になる）

## 案件開始時の初期化（セットアップ時に1回だけ）

1. `.gitignore` を**最初に**作る（内容は下記「.gitignoreの基本」が正。特に `hearing_*.json` の除外を忘れない）
2. `git init`（このフォルダをGit管理下にする）
3. `git add -A` → `git commit -m "chore: プロジェクト初期セットアップ"`（開始時点を記録。いつでもここに戻れる保険になる）
4. リモートに置く場合はGitHubで**プライベート**リポジトリを作成 → `git remote add origin <URL>`（手元のリポジトリとGitHubを紐付ける）→ `git push -u origin main`（初回push＋以後 `git push` だけで済む追跡設定）

.gitignore の内容は本スキルの「.gitignoreの基本」が正（作業手順書 Phase 1-5 は本節を参照する）。テンプレセットアップの全体像は作業手順書を参照。

## 基本の日常フロー（1人で作業する場合）

1. 作業開始前に最新を取り込む: `git pull origin ブランチ名`（リモートの最新の状態を自分の手元に取り込む）
2. コーディング作業をする
3. 変更内容を確認: `git status`（今どのファイルが変更されているか一覧で見る）
4. 変更を保存対象に追加: `git add .`（変更したファイルすべてを次のコミットに含める）
5. 記録として保存: `git commit -m "内容が分かるメッセージ"`（ここまでの変更をひとまとまりの履歴として保存する）
6. リモートに反映: `git push origin ブランチ名`（保存した履歴をGitHub等のリモートに送る）

Claude Code環境では、コミット操作に `/commit-commands:commit` プラグイン（差分を確認して規約に沿ったメッセージでコミットする）を使ってよい（CLAUDE.mdのGit運用と共通）。

## ブランチ運用

- `main`（または`master`）ブランチには直接コミットしない。作業用のブランチを切って進める
- ブランチ名は用途が分かる形にする（例: `feature/header`, `fix/form-validation`, `feature/animation-hero`）
- 新しいブランチの作り方: `git checkout -b feature/header`（`feature/header`という新しいブランチを作って、そこに切り替える）
- 作業が終わったら、`main`にマージ（統合）する前にプルリクエスト（GitHub上でのレビュー依頼）を作るのが望ましい。案件のチーム運用に合わせる

## コミットメッセージ規約

- 日本語で、変更内容が一目で分かるように書く（「更新」「修正」だけは避ける）
- 先頭に種別を付けると分かりやすい:
  - `fix:` バグ修正（例: `fix: フォームのバリデーションエラーを修正`）
  - `feat:` 新機能・新規実装（例: `feat: ヘッダーのアニメーションを追加`）
  - `style:` 見た目のみの調整（機能に影響しないCSS等）
  - `docs:` ドキュメントのみの変更
  - `chore:` 設定ファイルなど雑務的な変更

## トラブル時によくある操作

- 直前のコミットメッセージを間違えた: `git commit --amend` は settings.json で deny 済みのためClaude側では実行できない。メッセージ修正が必要なら人間が自分のターミナルで `git commit --amend -m "正しいメッセージ"` を実行する（push済みのコミットには使わない）
- コミット前の変更をなかったことにしたい: `git restore <ファイル名>`（そのファイルの未保存の変更を捨てて直前のコミットの状態に戻す。⚠️変更が消えるので、対象ファイルを絞って本当に不要か確認してから使う）
- 今どのブランチにいるか確認したい: `git branch`（一覧表示。今いるブランチには`*`が付く）
- リモートの状態と食い違ってpushできない: まず `git pull origin ブランチ名` を試す。それでも解決しない場合はコンフリクト（競合）が起きている可能性があるので、状況を貼ってもらえれば個別に案内する
- 作業途中だけど急ぎで別ブランチに移りたい: `git stash`（今の変更を一時的に棚にしまう）→ 用事が済んだら `git stash pop`（しまった変更を取り出して戻す）
- コンフリクトが起きた場合の基本: 慌てて操作せず、①`git status`で競合ファイルを確認 → ②該当ファイルを開き `<<<<<<<`〜`>>>>>>>` の目印で囲まれた「自分の変更」と「相手の変更」のどちらを残すか編集 → ③`git add` → `git commit` で解消。判断に迷ったらファイル内容を貼ってもらえれば一緒に見る

## .gitignoreの基本

- Web制作案件では以下を除外するのが基本（案件の技術構成に応じて調整）。**.gitignore は行末コメントを解釈しない**（`パターン   # 説明` と書くと `#` 以降もパターンの一部になり、その行は何も除外しなくなる）ので、コメントは必ず独立した行に書く:
```
node_modules/
.DS_Store
dist/
*.log
.env
# ヒアリングJSON。サーバー・ドメインの認証情報を含みうるため必ず除外（hearing-import参照）
hearing_*.json
```
- WordPress案件でテーマのみを管理する場合は、テーマフォルダ直下でリポジトリを作るのがシンプル。WordPress全体を管理する場合は以下も除外する:
```
# DB接続情報を含むため
wp-config.php
# メディアはGit管理しない
wp-content/uploads/
# プラグインは管理画面で管理（自作プラグインがある場合は個別に除外解除）
wp-content/plugins/
```
※ `acf-json/` はフィールド定義の共有に必要なので**除外しない**（wordpress-developmentスキル参照）

## デプロイ準備（公開作業に入る前のGit側の手順）

site-deploymentスキルで公開作業に入る前に、Git側で以下を済ませる。

1. 作業ブランチをすべて `main` にマージし、`git status` がクリーン（未コミットの変更なし）であることを確認する
2. ビルドが必要な案件は本番用ビルドを実行し（例: `npm run build`）、**成果物（`dist/` 等）の中身をブラウザで一度確認**してからアップに進む（ビルド忘れ・古い成果物のアップが定番事故）
3. 公開時点にタグを打っておくと、後から「公開した瞬間の状態」に戻れる: `git tag v1.0 && git push origin v1.0`（この時点の履歴に名前を付けてリモートにも送る）
4. アップ対象に `.git/`・`node_modules/`・ビルド前ソースが混ざっていないか確認する（除外の考え方はsite-deployment参照）

## 出力形式

- 通常は「今やるべき次の1手」としてコマンドと一言説明をセットで提示する
- 複雑な操作（リベース、コンフリクト解消等）は、まず現状（`git status`の出力やエラー内容）を教えてもらった上で個別に案内する
