# Git運用ルール

Web制作の実案件でGitを使う際のブランチ運用・コミットメッセージ規約と、初心者向けの操作説明をセットにしたルール。

## 前提：ユーザーはGit操作に不慣れ

- コマンドを提示する際は、コマンドだけでなく **「何をするコマンドか」を一言添える**（例: `git add .` ← 変更したファイルを『次の保存対象』に入れる操作）
- いきなり複数コマンドを羅列せず、今の状況で次に打つべき1〜2個に絞って案内する
- エラーが出た場合は、エラーメッセージの内容を噛み砕いて説明してから対処法を出す（英語のエラーをそのまま貼るだけにしない）
- 破壊的な操作（`git reset --hard`, `git push --force`, `git checkout .`で変更を捨てる等）を勧める前には、必ず「これをやると◯◯が消えます」と影響を説明し、了承を得る

## 基本の日常フロー（1人で作業する場合）

1. 作業開始前に最新を取り込む: `git pull origin ブランチ名`（リモートの最新の状態を自分の手元に取り込む）
2. コーディング作業をする
3. 変更内容を確認: `git status`（今どのファイルが変更されているか一覧で見る）
4. 変更を保存対象に追加: `git add .`（変更したファイルすべてを次のコミットに含める）
5. 記録として保存: `git commit -m "内容が分かるメッセージ"`（ここまでの変更をひとまとまりの履歴として保存する）
6. リモートに反映: `git push origin ブランチ名`（保存した履歴をGitHub等のリモートに送る）

## ブランチ運用

- `main`（または`master`）ブランチには直接コミットしない。作業用のブランチを切って進める
- ブランチ名は用途が分かる形にする（例: `feature/header`, `fix/form-validation`, `feature/animation-hero`）
- 新しいブランチの作り方: `git checkout -b feature/header`（`feature/header`という新しいブランチを作って、そこに切り替える）
- 作業が終わったら、`main`にマージ（統合）する前にプルリクエスト（GitHub上でのレビュー依頼）を作るのが望ましい。案件のチーム運用に合わせる

## コミットメッセージ規約

- 日本語で、変更内容が一目で分かるように書く（「更新」「修正」だけは避ける）
- 先頭に種別を付けると分かりやすい:
  - `fix:` バグ修正（例: `fix: フォームのバリデーションエラーを修正`）
  - `feat:` 新機能・新規実装（例: `feat: ヘッダーのアニメーションを追加`）
  - `style:` 見た目のみの調整（機能に影響しないCSS等）
  - `docs:` ドキュメントのみの変更
  - `chore:` 設定ファイルなど雑務的な変更

## トラブル時によくある操作

- 直前のコミットメッセージを間違えた: `git commit --amend -m "正しいメッセージ"`（直前の保存内容のメッセージだけ書き換える）
- コミット前の変更を全部なかったことにしたい: `git checkout .`（⚠️保存していない変更が消えるので、本当に不要か確認してから使う）
- 今どのブランチにいるか確認したい: `git branch`（一覧表示。今いるブランチには`*`が付く）
- リモートの状態と食い違ってpushできない: まず `git pull origin ブランチ名` を試す。それでも解決しない場合はコンフリクト（競合）が起きている可能性があるので、状況を貼ってもらえれば個別に案内する
- 作業途中だけど急ぎで別ブランチに移りたい: `git stash`（今の変更を一時的に棚にしまう）→ 用事が済んだら `git stash pop`（しまった変更を取り出して戻す）
- コンフリクトが起きた場合の基本: 慌てて操作せず、①`git status`で競合ファイルを確認 → ②該当ファイルを開き `<<<<<<<`〜`>>>>>>>` の目印で囲まれた「自分の変更」と「相手の変更」のどちらを残すか編集 → ③`git add` → `git commit` で解消。判断に迷ったらファイル内容を貼ってもらえれば一緒に見る

## .gitignoreの基本

- Web制作案件では以下を除外するのが基本（案件の技術構成に応じて調整）:
```
node_modules/
.DS_Store
dist/
*.log
.env
```
- WordPress案件でテーマのみを管理する場合は、テーマフォルダ直下でリポジトリを作るのがシンプル。WordPress全体を管理する場合は以下も除外する:
```
wp-config.php        # DB接続情報を含むため
wp-content/uploads/  # メディアはGit管理しない
wp-content/plugins/  # プラグインは管理画面で管理（自作プラグインがある場合は個別に除外解除）
```
※ `acf-json/` はフィールド定義の共有に必要なので**除外しない**（wordpress-developmentスキル参照）

## 出力形式

- 通常は「今やるべき次の1手」としてコマンドと一言説明をセットで提示する
- 複雑な操作（リベース、コンフリクト解消等）は、まず現状（`git status`の出力やエラー内容）を教えてもらった上で個別に案内する
