# ヒアリング・見積もり

受注前フェーズの標準手順。見積もりの精度は**ヒアリングの精度**で決まるため、金額を出す前に要件の穴を潰すことを最優先にする。

## 1. ヒアリング項目

初回ヒアリングで確認する標準セット。案件規模に応じて取捨選択する。

### 目的・前提

- サイトの目的（問い合わせ獲得 / 採用 / ブランディング / EC）と、**成果として何が増えれば成功か**
- 新規かリニューアルか。リニューアルなら現サイトの不満点と、引き継ぐもの（ドメイン、コンテンツ、SEO資産）
- ターゲット（誰に見せたいか）と、参考サイト2〜3件（「この雰囲気が好き」の共有が後のデザイン齟齬を防ぐ）
- **納期と、その納期の理由**（イベント・広告出稿等の絶対期限か、希望か）

### 範囲・素材

- ページ数と構成（サイトマップ）。未確定なら概算の前提を置き、見積もりに明記する
- **原稿・写真は誰が用意するか**（クライアント支給 / 制作側で作成・手配）。ここが曖昧なまま受けると進行が止まる最大要因
- デザインの範囲: デザインから担当か、支給カンプのコーディングのみか
- 対応ブラウザ・デバイスの範囲
- フォーム・ブログ等の機能要件。更新性が必要ならWordPress化の要否（wordpress-development）

### 環境・運用

- サーバー・ドメインの契約状況と契約者（site-deploymentの前提確認と共通）
- 公開後の更新は誰がやるか。保守契約の要否（wp-maintenance-inspection）
- 解析（GA4等）の導入要否（analytics-setup）

### 予算

- 予算感は聞けるなら聞く。答えにくそうなら「○○万円だと△△まで、□□万円だと〜」と松竹梅で当てる方法もある

## 2. 工数見積もりの考え方

### 基本式

**見積額 = 作業工数（時間）× 時間単価 + 外部費用（素材購入・サーバー等の実費）**

時間単価はユーザー自身の設定によるが、フリーランスのWeb制作では**時給換算3,000〜5,000円程度を下限の目安**にする（これを下回ると事業として回らない）。単価を上げる場合は作業ではなく成果（集客・採用への貢献）で語る。

### 工数の積み上げ

ページ単位・機能単位で分解して積む。分解の粒度の例:

- トップページのコーディング（他ページの1.5〜2倍を見る）
- 下層ページのコーディング × ページ数（同一レイアウトの量産は2枚目以降を減額）
- お問い合わせフォーム（確認画面あり/なしで差が出る。form-implementation）
- WordPress化（テンプレート数 × 単価。ACF設計含む。wordpress-development）
- アニメーション実装（animation-implementation。凝った演出は別途明記）
- SEO・OGP設定、解析導入、公開作業（seo-meta-implementation / analytics-setup / site-deployment）
- テスト・検収対応、進行管理（**実装工数の15〜20%を目安に必ず計上**する。忘れると確実に赤字化する項目）

### バッファと修正回数

- 見積もり全体に10〜20%のバッファを乗せる（要件の揺れ・想定外の吸収分）
- **修正回数の上限を見積書に明記する**（例: デザイン修正2回まで、以降は別途）。無限修正の防止はここでしか効かない

## 3. 見積書・提案書の構成

### 見積書に必ず書くこと

- 項目別の金額（一式○○円のドンブリにしない。項目分解は減額交渉時に「どれを削るか」の会話を可能にする）
- **含まれないもの**（原稿作成、写真撮影、ロゴ制作、保守、サーバー費 等）。トラブルの9割は「含まれると思っていた」から起きる
- 修正回数の上限、有効期限、支払条件（着手金の有無。50%着手時・50%納品時が標準的）
- 前提条件（素材はクライアント支給、ページ数○ページ想定 等。前提が崩れたら再見積もりの根拠になる）

### 提案書（必要な場合）

構成の型: 現状の課題 → 提案の方向性 → サイト構成案（wireframe-proposalスキルで叩き台を作れる）→ 制作範囲 → スケジュール → 概算費用 → 制作フロー。デザインの手戻りを防ぐため、**着手前に決まっていること・後で決めることを明示**する。

## 4. スコープ管理（受注後の追加要望）

- 追加要望が来たら「できます/できません」の前に、**元の見積もり範囲との差分**を判定する癖をつける
- 範囲外の場合の返し方: 「対応可能です。○○の追加となるため、+○円・納期+○日で見積もりします」— 断らずに条件を提示する
- 小さな追加を無償で受ける場合も「今回はサービスで対応します（通常○円相当）」と**価値を明示してから**受ける。黙って受けると次から標準になる
- 対応が難しい局面（値引き圧、大幅な仕様変更）では、返信文の作成を支援する。感情的にならず、条件と代替案をセットで返すのが基本形

## 5. 検収・納品・請求（受注時に決めておくこと）

トラブルは納品時に顕在化するが、原因は受注時の取り決め不足にある。見積書・発注書の段階で以下を決めておく。

- **検収期間を区切る**（例: 納品後2週間以内。期間内に連絡がなければ検収完了とみなす旨を明記）。区切らないと「公開から半年後の無償修正依頼」を断る根拠がなくなる
- **納品形態**を明示する: サーバー反映まで（公開して完了）か、データ一式の引き渡しか。データ納品の場合、ビルド前ソース（SCSS等）を含むかどうかも決める（含まないなら明記。後の改修者・existing-site-modificationの「src行方不明」問題の予防）
- **請求タイミング**: 着手金50% + 納品時50%が標準形。公開日がクライアント都合で延びるケースに備え、「納品（検収完了）基準」か「公開基準」かを決めておく（公開基準にすると延期分だけ入金も延びる）
- 納品物に含める資料: 引き継ぎ資料・規約書（coding-standards-doc）、解析の設定内容一覧（analytics-setup）の要否

## 出力形式

- ヒアリングシートを求められたら、上記項目を案件種別（新規/リニューアル、静的/WP）に合わせて絞って提示する
- 見積もりの相談では、ユーザーから聞いた条件で不足している前提（ページ数、素材支給の有無等）を先に確認してから概算を出す。**前提を置いた場合は必ず明記**する
- 金額の妥当性を問われたら、相場観と「その単価で時給いくらになるか」の逆算を添えて判断材料を出す（最終判断はユーザーに委ねる）
