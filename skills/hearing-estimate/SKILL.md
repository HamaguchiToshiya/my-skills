# ヒアリング・見積もり

受注前フェーズの標準手順。見積もりの精度は**ヒアリングの精度**で決まるが、**穴を潰しきってから金額を出すのは「正式見積もり」だけ**。受注が確定していない相手に全項目を投げると、金額を知りたいだけの人に要件定義の工数を負担させることになる。下の2段構えで進める。

## 0. 概算フェーズと正式見積もりフェーズ

**相談の時点では発注が確定していないことが多い**（クライアント側も要件を整理できていない／まず金額を把握して社内・取引先に提案したい）。この段階で細かい質問を大量に送ると、相手の負担だけが増えて見積もりも遅れる。

| | 概算フェーズ | 正式見積もりフェーズ |
|---|---|---|
| 目的 | 金額の桁を合わせて、話を先に進める | 契約できる金額を確定する |
| 聞く範囲 | **金額に大きく効く項目だけ**（下の最小6項目） | 「1. ヒアリング項目」の全項目 |
| 出し方 | 仮条件を明示した概算。必要ならA/B/C案 | 項目別の確定見積書 |
| 前提の扱い | 「この条件で算出。変われば金額も変わる」と先に伝える | 前提を確定し、崩れたら再見積もりの根拠にする |

### 概算に必要な最小6項目

1. **ページ数**（おおよそでよい。「5〜7ページ想定」で置ける）
2. **デザインの範囲**（デザインから／支給カンプのコーディングのみ）
3. **原稿・写真の支給有無**（撮影・原稿作成が入ると桁が変わる）
4. **フォーム・更新機能の有無**（WordPress化の要否）
5. **納期**（絶対期限か希望か）
6. **予算感**（答えにくそうなら松竹梅で当てる）

これ以外（対応ブラウザ、サーバー契約者、解析、保守）は**概算では聞かずに仮条件で置く**。薬機法・景表法のリスク確認（下記）だけは例外で、該当業種なら概算の段階で確認する（工数の桁が変わるため）。

### 不明点は仮条件を置いて出す

「現時点ではこの条件で算出しています」と前提を並べて概算を出す。例: 「5〜7ページ想定」「フォーム1つ・確認画面なし」「原稿と写真は支給」「外部サービス連携なし」「WordPress化なし」。

**振れ幅が大きいときは1つの金額に絞らない。**

- **A案**: 既存コンテンツ・素材を活かした最小構成
- **B案**: デザイン制作＋基本機能のベーシック構成
- **C案**: 撮影・原稿作成まで含むフル構成

相手は金額だけでなく「**どこまで依頼するか**」を同時に判断できる。あわせて下限（最低これくらいはかかる）・上限（◯◯万円を超えることはない）を伝えると、レンジ提示が「見積もりが曖昧」ではなく「範囲が違えば費用も違う」として伝わる。

概算の予算感が合ってから、細かい要件を詰めて正式見積もりに落とす。そのとき「この機能は本当に必要か」「もっと簡単な方法はないか」「後から追加になりそうなものはないか」をこちら側で整理して、必要／不要を分けながら金額を固める。

## 1. ヒアリング項目

初回ヒアリングで確認する標準セット。案件規模に応じて取捨選択する。**これは正式見積もりフェーズで潰す全項目**で、概算段階では §0 の最小6項目に絞る。

### 目的・前提

- サイトの目的（問い合わせ獲得 / 採用 / ブランディング / EC）と、**成果として何が増えれば成功か**
- 新規かリニューアルか。リニューアルなら現サイトの不満点と、引き継ぐもの（ドメイン、コンテンツ、SEO資産）
- **他社制作サイトの引き継ぎ・移管は、次の5点が揃うまで着手日を確定しない**: ①ソースコード一式（＋ロゴ等の元データ）②サーバーの認証情報 ③ドメインの管理権限と AuthCode（**ドメインが前の制作会社名義になっていないか**）④CMSの管理者権限 ⑤著作権の扱い。取り寄せるのはクライアントで、引き渡し拒否や買取費用の請求はクライアント側のリスクとして見積もり前に伝える
- ターゲット（誰に見せたいか）と、参考サイト2〜3件（「この雰囲気が好き」の共有が後のデザイン齟齬を防ぐ）
- **納期と、その納期の理由**（イベント・広告出稿等の絶対期限か、希望か）

### 範囲・素材

- ページ数と構成（サイトマップ）。未確定なら概算の前提を置き、見積もりに明記する
- **原稿・写真は誰が用意するか**（クライアント支給 / 制作側で作成・手配）。ここが曖昧なまま受けると進行が止まる最大要因
- デザインの範囲: デザインから担当か、支給カンプのコーディングのみか
- 対応ブラウザ・デバイスの範囲
- フォーム・ブログ等の機能要件。更新性が必要ならWordPress化の要否（wordpress-development）

### 環境・運用

- サーバー・ドメインの契約状況と契約者（site-deploymentの前提確認と共通）
- 公開後の更新は誰がやるか。保守契約の要否（wp-maintenance-inspection）
- 解析（GA4等）の導入要否（analytics-setup）

### 広告表現のリスク確認（医療・美容・健康食品・エステ系の案件では必須）

薬機法・景表法に抵触しうる表現の有無を受注前に確認し、表現チェック・修正往復の工数を見積もりに含める。デザイン検証（design-verification STEP 1a #12）が裏付けのない実績数値・効果表現を検出したときの照合先もここ。

- NG表現の型: 効果効能の断定（「治る」「痩せる」）/ 根拠資料のない最上級・No.1表現 / ビフォーアフター写真の扱い / 体験談の引用（打消し表示の要否）
- 疑わしい表現は勝手に直さず、**必ずクライアント確認に回す**（代替表現の提案はしてよい）
- **法適合の最終責任はクライアント側**であることを見積書・契約の前提条件に明記する（制作側は「広告表現の法務チェックは業務範囲外」と線を引く。法改正の追跡はしないため、具体的な適法判断は専門家に委ねる）

### 予算

- 予算感は聞けるなら聞く。答えにくそうなら「○○万円だと△△まで、□□万円だと〜」と松竹梅で当てる方法もある

## 2. 工数見積もりの考え方

### 基本式

**見積額 = 作業工数（時間）× 時間単価 + 外部費用（素材購入・サーバー等の実費）**

時間単価はユーザー自身の設定によるが、フリーランスのWeb制作では**時給換算3,000〜5,000円程度を下限の目安**にする（これを下回ると事業として回らない）。単価を上げる場合は作業ではなく成果（集客・採用への貢献）で語る。

### 工数の積み上げ

ページ単位・機能単位で分解して積む。分解の粒度の例:

- トップページのコーディング（他ページの1.5〜2倍を見る）
- 下層ページのコーディング × ページ数（同一レイアウトの量産は2枚目以降を減額）
- お問い合わせフォーム（確認画面あり/なしで差が出る。form-implementation）
- WordPress化（テンプレート数 × 単価。ACF設計含む。wordpress-development）
- アニメーション実装（animation-implementation。凝った演出は別途明記）
- SEO・OGP設定、解析導入、公開作業（seo-meta-implementation / analytics-setup / site-deployment）
- テスト・検収対応、進行管理（**実装工数の15〜20%を目安に必ず計上**する。忘れると確実に赤字化する項目）

### バッファと修正回数

- 見積もり全体に10〜20%のバッファを乗せる（要件の揺れ・想定外の吸収分）
- **修正回数の上限を見積書に明記する**（例: デザイン修正2回まで、以降は別途）。無限修正の防止はここでしか効かない

## 3. 見積書・提案書の構成

### 見積書に必ず書くこと

- 項目別の金額（一式○○円のドンブリにしない。項目分解は減額交渉時に「どれを削るか」の会話を可能にする）
- **含まれないもの**（原稿作成、写真撮影、ロゴ制作、保守、サーバー費 等）。トラブルの9割は「含まれると思っていた」から起きる
- 修正回数の上限、有効期限、支払条件（着手金の有無・タイミングの標準形は下記「5. 検収・納品・請求」の請求タイミングを参照）
- **著作権の帰属（譲渡するかしないか）と実績掲載の可否**。譲渡すると自分の実績転用・他案件への流用ができなくなるので、どちらにするかを必ず書く。**再委託の可否**（事前承認制が標準）も同じ場所で決める
- 前提条件（素材はクライアント支給、ページ数○ページ想定 等。前提が崩れたら再見積もりの根拠になる）
- **概算を出す場合**は「概算」と明記し、仮条件を列挙する。振れ幅が大きければA/B/C案＋下限・上限で出す（§0）

### 提案書（必要な場合）

構成の型: 現状の課題 → 提案の方向性 → サイト構成案（wireframe-proposalスキルで叩き台を作れる）→ 制作範囲 → スケジュール → 概算費用 → 制作フロー。デザインの手戻りを防ぐため、**着手前に決まっていること・後で決めることを明示**する。クライアントに見せる形は `wireframe-proposal` の**提案1枚HTML**（雛形と運用ルールは同スキルが正）に載せる——提案書を別フォーマットで組み直さない。

## 4. スコープ管理（受注後の追加要望）

- 追加要望が来たら「できます/できません」の前に、**元の見積もり範囲との差分**を判定する癖をつける
- 範囲外の場合の返し方: 「対応可能です。○○の追加となるため、+○円・納期+○日で見積もりします」— 断らずに条件を提示する
- 小さな追加を無償で受ける場合も「今回はサービスで対応します（通常○円相当）」と**価値を明示してから**受ける。黙って受けると次から標準になる
- 対応が難しい局面（値引き圧、大幅な仕様変更）では、返信文の作成を支援する。感情的にならず、条件と代替案をセットで返すのが基本形

## 5. 検収・納品・請求（受注時に決めておくこと）

トラブルは納品時に顕在化するが、原因は受注時の取り決め不足にある。見積書・発注書の段階で以下を決めておく。

- **検収期間を区切る**（例: 納品後2週間以内。期間内に連絡がなければ検収完了とみなす旨を明記）。区切らないと「公開から半年後の無償修正依頼」を断る根拠がなくなる
- **契約不適合責任の期間を合意する**（例: 公開後6ヶ月〜1年。この期間内のバグ・表示崩れ・実装漏れは無償対応、以降は別途）。検収完了後の修正依頼の線引き（billing-paperwork）はここで合意した期間を前提に動くため、決めずに受注しない
- **納品形態**を明示する: サーバー反映まで（公開して完了）か、データ一式の引き渡しか。データ納品の場合、ビルド前ソース（SCSS等）を含むかどうかも決める（含まないなら明記。後の改修者・existing-site-modificationの「src行方不明」問題の予防）
- **請求タイミング**: 着手金50% + 納品時50%が標準形。公開日がクライアント都合で延びるケースに備え、「納品（検収完了）基準」か「公開基準」かを決めておく（公開基準にすると延期分だけ入金も延びる）
- 納品物に含める資料: 引き継ぎ資料・規約書（coding-standards-doc）、解析の設定内容一覧（analytics-setup）の要否
- **保守契約を提案する場合の条件設計もここで行う**（月額・作業範囲・点検頻度・連絡窓口。点検メニューの実体は `wp-maintenance-inspection` を参照して工数を見積もる）。**障害対応を含めるかどうかが保守の最大の分岐**——含めるなら対応時間帯と復旧目標を書く（曖昧にすると「サイトが落ちた」の一報で青天井に時間を吸われる）。運用・保守は請負ではなく準委任にしておく
- ここで決めた条件（検収期間・納品形態・請求タイミング）の**納品時の実行は `billing-paperwork` が担当**（納品連絡・検収依頼・請求書・催促の文面はそちらが正）
- クライアント記入のヒアリングシート（JSON）の取り込み・整理は、届いた時点でフェーズを問わず `hearing-import` が担当。**シートが受注前に届いた場合は、hearing-import の出力 `docs/hearing-notes.md` の「hearing-estimate用材料」を本スキルの入力にする**（口頭ヒアリングのみの案件では本スキルの整理メモがそのまま材料になる）

## 出力形式

- 見積書・提案書・ヒアリングシートをドキュメントとして求められた場合は、実ファイル（Markdown等）として作成する
- ヒアリングシートは上記項目を案件種別（新規/リニューアル、静的/WP）に合わせて絞って提示する
- 見積もりの相談では、まず概算か正式かを見極める（§0）。概算なら最小6項目だけ確認し、残りは仮条件で置いて出す。**前提を置いた場合は必ず明記**する
- 金額の妥当性を問われたら、相場観と「その単価で時給いくらになるか」の逆算を添えて判断材料を出す（最終判断はユーザーに委ねる）
