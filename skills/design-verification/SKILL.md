# デザイン検証チェックリスト（AIスロップ検出）

design-taste で方向を決めて実装したページが、「AIが作った量産デザイン」に落ちていないかを検証する。**デザイン検証の判定基準は本スキルが正典**（作るときの基準は `design-taste` Phase 1〜6、検証の基準は本スキル）。

**線引き**: alt・meta・コンソールエラー等のコード品質は `pre-delivery-checklist`、アニメーションの実装作法は `animation-implementation` の担当。本スキルは**見た目とコピーのAIっぽさ**だけを見る。例外として STEP 1a #29〜#32（フォーカスリング・インタラクティブ状態・minmax・sticky）と #39〜#41（ベースラインずれ・大見出しの折返し保護・all-caps行間）は実装起因だが「AIっぽさ」が見た目に露呈する項目のため本スキルが持つ（#29/#30 は `form-implementation` がゲート参照している。番号を変えない）。

**#34〜#44・STEP 1b #6・#7 は較正前**——表の基準が ERROR でも 🔴 に落とさない。**通常の WARN とも混ぜず、レポートの「要検証（較正前項目・判定保留）」枠に分けて書く**（総合判定には数えない。書式は `references/report-template.md`）。検証できていないものを「問題なし」にも「WARN」にも丸めないための分離で、この枠に溜まる「このケースで基準は妥当か」の評価が較正の材料になる。較正の進め方・解除条件は checks.md の STEP 1a 節冒頭の但し書きが正。

**前提**: 検証はプロジェクトの design-taste の設定値（VARIANCE / MOTION / DENSITY と定義済みパレット。通常 `design-brief.md` に記載）を正として行う。design-brief.md が無い場合、CLAUDE.md にデザイン方針の宣言があればそれを**暫定ブリーフとして監査してよい**（テイスト照合は保留と明記。design-checker の鉄則・作業手順書と同運用）。どちらも無ければ先に確認する。

**数値の同期**: STEP 1a の閾値の多くは design-taste Phase 4〜5 と対で同じ値を持つ（対応の索引は `design-taste/references/visual-craft.md` の「design-verification との数値同期表」）。**閾値を改訂するときは同期表を辿って design-taste 側も同時に更新する**。

**実行詳細の置き場**: 判定方法・基準・grepコマンドの正は `references/checks.md`（#34〜#44・STEP 1b #6・#7 で取り込まなかった項目の担当先もその冒頭にある）。レポートのテンプレートは `references/report-template.md`。本ファイルが持つのは全体像・項目一覧・致命判定・運用ルール。

## 運用ルール

- 監査→修正のループは**3回まで**。3回目でも重要度: 高の ERROR が残る場合は人間の判断にエスカレーションする（レポートに「要人間判断」と明記）
- **ループの状態は会話ではなくレポートで管理する**。ラウンド番号と前回ERROR対応表はレポート冒頭の「監査情報」（出力形式参照）が正。再監査時は前回レポートを読んでラウンドを+1し、対応表に「残存」が1件でもあれば次項の (a)（同一ERRORの2周目）に該当する。コンパクションやセッションを跨いでも、レポート単体で回数・エスカレーション条件を復元できる状態を保つ
- **参考不足系の指摘は実例収集でエスカレーションする**: (a) 同一 ERROR が2周目でも残った場合、または (b) 指摘の原因が「参考の不在」にある場合（STEP 2 の量産感系症状・ダイヤル値との乖離・無難化・余白/タイポの質感系）、本体は `design-researcher` を**ピンポイントモード**（3サイト前後・症状特化）で起動し、その症状を回避している実例を集めて designer への修正指示に添える（「直せ」だけでなく「こう直っている実例」を渡す）。**毎周は回さない**（ループのテンポ優先。通常の ERROR はそのまま修正に回す）。調査中も他の指摘の修正は先に進めてよい
- 総合判定は3値（agents/README の判定ラベル統一と対応）: **🟢 合格**＝ERROR・WARNともなし / **🟡 条件付き合格**＝ERRORなし・WARNあり、または「要人間判断」が残存（納品可・改善は任意。**修正ループは回さない**）/ **🔴 要修正**＝ERRORあり
- WARN は納品を止めない。**重要度: 高の ERROR が1件でもあればリビジョン要**
- 判定に迷う項目は ERROR にせず WARN ＋「要人間判断」とする。過剰な ERROR で修正ループを空転させない
- 再検証時は前回レポートの ERROR 項目を優先確認し、新規項目は差分中心に見る

### 修正の原因4分類（designer の修正モードが読む）

ERROR に対応する前に指摘の原因を4分類し（①トークン欠落＝再利用値を定義すべき / ②一点物実装＝既存の共通パターンに置き換えるべき / ③概念のズレ＝階層・構成が他セクションと食い違う / ④局所欠陥＝単なる実装不備）、**最も狭い正しいレベルで直す**（④を①として直すとトークンが増殖し、①を④として直すと同じ指摘が別の場所で再発する）。

## 出力形式

検証結果はプロジェクトの実ファイル `design-check-report.md` として出力する。**書き出す前に必ず `references/report-template.md` を読み、そのテンプレートと記載ルールに従う**（対象別のファイル分割・「監査情報」のラウンド管理欄・判定ラベル OK / WARN / ERROR / 未検証 の4種＋較正前項目専用の「要検証」・数値根拠の書き方を含む）。

対応レビューエージェント: `design-checker`（Playwright実測・スクリーンショット目視の実行手段を持つ）
