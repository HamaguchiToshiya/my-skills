# design-verification 実行詳細（checks）

`../SKILL.md`（design-verification）の各STEP実行時に読む詳細。**判定方法・基準・grepコマンドの正はこのファイル**（項目の見出し・番号の一覧と致命判定・運用ルールは SKILL.md 側）。チェック項目の追加・改廃は SKILL.md 側の一覧と同時に行い、#番号は振り直さない。

## #34〜#44・STEP 1b #6・#7 の線引き（取り込まなかった項目の担当先）

**#34〜#44・STEP 1b #6・#7 は、外部の検証ゲート集と既存33項目を突き合わせ、本スキルに無かった項目だけを翻案した項目群。** 取り込まなかったものの理由と担当先を残す——書体の既定リスト（Inter/Poppins 等の禁止）は和文案件で Noto Sans JP を排除できないため不採用（**同趣旨は design-taste 4-2 の「Noto Sans JP 一本＝和文版 Inter症候群」が既にカバー**）、トースト・ツールチップ遅延・カルーセルの一時停止は `js-implementation-standard`、動画のLCP対策は `performance-optimization`、装飾SVGの `aria-hidden` は `pre-delivery-checklist`、マクロ構造スタンプ等は本スキルの仕組みに無いため対象外。

## STEP 1a: 静的チェック（コードのgrep・カウント）

以下を実際にカウント・検索して判定する。基準を満たさないものは ERROR として報告する。

**#34〜#44・STEP 1b #6・#7 は較正前（実案件で未検証）**。閾値が実データに当たっていないので、**当面は判定を保留して運用する——表の基準が ERROR でも 🔴 に落とさず、通常の WARN とも混ぜずにレポートの「要検証（較正前項目・判定保留）」枠に書く**（総合判定には数えない。枠の書式は `report-template.md`）。枠には毎回「このケースで基準は妥当か」を1行で書き残す——**この評価の蓄積が較正の実データになる**。誤検知の実績が出た項目は閾値を直し、2案件で誤検知ゼロを確認できたものからこの但し書きの対象外にして本記載どおりの判定に上げる。**#34（余白の直値）が最も引っかかりやすい**見込み——既存案件はスケール外の余白を持っている前提なので、WARN 5件→ERROR の線は実測してから決める。較正が済んだ項目はこの段落から番号を消す（**全部消えたらこの段落ごと削除**）。番号を消すときは SKILL.md 側の一覧の※印・1行注記も同時に消す。

- ビューポートは **375×812（SP）と 1440×900（PC）の両方**で確認する。横あふれと見出しの改行位置は **360×780 でも追加確認**する（Galaxy S 系・iPhone 12 mini など現行機の最小幅。375 で通っても 360 で1文字送りや横スクロールが出る事故が典型。根拠: vault「モバイルデザインの基準幅は375pxより400px」）
- 実測は `design-checker` エージェント（Playwright実測の実行手段を持つ）または人間の実機確認で行う。実行環境がない場合はコードからの推定で埋めず「未実測」と明示する

実測の作法（測定側の落とし穴。ここを外すと正常品を不合格に、不良品を合格にする）:

- **スクロール連動の状態を実測する前に `html { scroll-behavior: auto !important }` を注入する**。ページCSSに `smooth` があると `window.scrollTo()` がアニメーションになり、待ち時間内に目標位置へ届かないまま読んでしまう（演出が「凍結」して見える誤診の典型）。`scrollTo` 後は実 `scrollY` を目標値と突き合わせてから opacity 等を読む
- **改行・折り返し（1bの項目4）は「素のDOM」と「演出適用後」の両方で検証する**。SplitText 等のchar分割は各文字をinline-block化し、折り返し位置も禁則も素のDOMと変わるため、reduced-motion だけの検証では本番の壊れ方を見逃す
- **マスコット・アイコン等の小さいグラフィックは、要素単体を `deviceScaleFactor` を上げた拡大ショットで検証する**。フルページ撮影は配置確認にしか使えない（同色パーツの埋もれ・重なり順は等倍では判別できない）
- **ファーストビュー（1bの項目2）はPC 1440×900に加えて 1280×800 でも確認する**。13インチ実機で最も割れやすいのがこの幅。収まらない場合の主犯は、見出し `clamp()` の上限過大・見出し行間の緩み・リード文3行超・ヒーローの `padding` 過大の4つ（文字を極端に小さくする方向で直さない）
- **横スクロール（1bの項目3）の封じ込めは `html, body { overflow-x: clip }`**。`hidden` でなく `clip` を使う（`hidden` は内部の `position: sticky` を殺すが、`clip` は保持する）。ただしこれは保険であり、原因（はみ出している要素・1aの項目31等）の特定と修正が先
- **通しのフルページ撮影は reduced-motion（`reducedMotion: 'reduce'`）で行う**。GSAP の `.from()` は未発火の要素を初期値（opacity:0 等）のまま保持するため、通常モードの fullPage 撮影は折り返しより下が消えて写る。reduced-motion なら全要素が静的な最終状態で描画され、「演出を止めても静的に成立するか」の確認も兼ねられる
- **測定スクリプトを新調・改造するときは、書く前に** vault の `実装が壊れて見えたらまず測定器を疑う` のチェック手順を通す（操作が反映されたかを実 `scrollY` 等の突き合わせで確認してから値を読む）。罠は実装コードだけでなく**測定手順に再発する**——ノートが在っても、引く習慣が無ければ無いのと同じ
- **比較のための計測コード（A/B比較・前後比較・書体比較等）には、比較が成立していないことを検出する行を入れる**（例: 両条件で同一要素を測れているかの照合、rect が2回連続で一致するまで待ってから採る、等）。比較の前提が崩れたまま数値だけが出るのが測定事故の典型で、「測定は通るのに別のものを測っていた」を機械的に検出できる形にする
- **将来案（未実装）**: コントラスト比（1bの項目1）は現状 `color` と実効背景色からの算出だが、スクリム・グラデーション・画像の上のテキストは「テキストだけ隠して同フレームを再撮影し、実描画のピクセルから背景輝度を採る」方式のほうが確実（scroll-craft の verify 手法。導入するなら design-checker のスクリプト側）

## STEP 2: AI判断チェック（症状ベース）

以下の複合症状が出ていないかを見る。該当したら「どのセクションが・なぜそう見えるか」を必ず特定して報告する。

- [ ] **テンプレ・ヒーロー**: 中央寄せ見出し＋中央寄せサブテキスト＋中央CTA＋背景グラデの4点セット。VARIANCE 5以上の設定なら非対称構成（分割・オフセット・重なり）になっているべき
- [ ] **ヒーロー要素過多**: ファーストビューの要素が見出し・サブテキスト・CTA・ビジュアルの4つを超えて詰め込まれていないか。サブテキストが2文以上の説明文になっていないか
- [ ] **AIテンプレ骨格**: ページ全体が「ヒーロー → 3特徴 → CTA → フッター」の並びそのままになっていないか。**#4 が「型の多様性」を見るのに対し、こちらは骨格の順序そのもの**を見る（型を4種使っていてもこの順序なら該当する）。セクションの順序に、その案件固有の理由（購買検討の順・不安の解消順・実績で信用を作ってから料金）があるか
- [ ] **ナビの既定形**: ワードマーク左＋中央に4〜5リンク＋右端にCTAボタン、の一択になっていないか。他の型は vault [[ヘッダーCTAの配置パターン6選]] [[ヘッダーメニューのデザインパターン7選]] [[ヘッダーメニューの変わり種デザイン5選]] にある。※定番であること自体は悪ではないので、**業種・情報量に対して他の型を検討した形跡があるか**で判断する（design-brief にヘッダー型の宣言があれば OK）
- [ ] **フッターの既定形**: 4列リンク＋SNSアイコン＋コピーライト、の一択になっていないか（vault [[フッターのデザインレイアウト16選 v2]]）。**中小事業サイトでは4列を埋めるリンクが無く、水増しした結果スカスカになる**のが典型的な失敗
- [ ] **全セクション同一リズム**: 余白・見出しサイズ・構成が全セクションで同じで、ページに緩急がないか（DENSITY設定との整合を見る）
- [ ] **余白のリズム不全**: セクション間の余白がスペーシングスケールに乗っていない。要素が均等間隔で並びグルーピング（親子・関連）が余白から読み取れない。詰まりすぎ／間延びした箇所がある
- [ ] **視線誘導の欠落**: ファーストビューで「最初に見る場所」が決められない（同じ視覚的強度の要素が並列）。CTAが色・サイズ・余白のいずれでも際立たず埋没。読み順が蛇行する配置に必然性がない
- [ ] **装飾の意図性欠如**: 「なぜここにあるか」を一文で説明できない図形・線・あしらいがある。あしらいの語彙が3種を超えて散らかっている。装飾がコンテンツの可読性を侵食している
- [ ] **アイコンカードの羅列**: 写真・イラスト・実データを使わず、汎用アイコン＋短文のカードだけで特徴セクションを済ませていないか
- [ ] **div製の偽プロダクトUI**: ヒーロー等でスクリーンショットの代わりに、divで組んだ偽ダッシュボード・偽ターミナル・偽タスクリストを置いていないか。**偽ブラウザ枠（URLピル＋信号ドット）・偽スマホ枠（角丸＋ノッチ）・偽コードウィンドウをCSS/SVGで自作するのも同罪**（ユーザーの環境に実在するchromeの再描画はAIテルの最有力）。実画像を `<figure>` で使うか、置かない
- [ ] **画像上の装飾ラベル**: 写真の上に `Brand · 02` 型のオーバーレイピルや、実在しない撮影クレジット風キャプション（`Frame XII · 35mm` 等）を載せていないか。キャプションが必要なら画像の外に実情報を1行
- [ ] **雰囲気メタ情報**: ロケール/時刻/天気ストリップ（`TOKYO 14:23 · 18°C`）等、実情報でない「それっぽさ」装飾がないか（実店舗の住所・営業時間・アクセスは該当しない）
- [ ] **見出し右上の浮遊テキスト**: 大見出しセクションの右上隅に、他の要素と整列しない小さな説明段落を浮かせていないか（見出し直下に置くか、2カラムで整列させる）
- [ ] **コピーの同型反復**: 見出しが全て同じ構文（「〜で、〜を。」「〜する、〜へ。」等）で並んでいないか。英語キャッチコピー混在時は「—」（emダッシュ）の多用もAIサインとして見る
- [ ] **ダイヤル値との乖離**: design-taste の設定（例: VARIANCE 8）に対して実装が保守的すぎる／過剰すぎる箇所はないか（テイストファミリー宣言に対する無難側への退行、業種制約を超えた過剰演出を含む）

- [ ] **複数ページの一貫性崩れ**（複数ページ案件のみ）: ページ間でトークン（色・角丸・見出しスタイル）が揺れていないか。下層ページが共通の型を共有しているか
