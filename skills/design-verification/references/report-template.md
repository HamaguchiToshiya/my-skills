# design-verification レポート出力形式

`../SKILL.md`（design-verification）の検証結果を書き出すときのテンプレートと記載ルール。

検証結果はプロジェクトの実ファイル `design-check-report.md` として出力する（design-checker エージェント使用時・手動検証時とも同形式）。TOPと下層など監査対象が複数ある案件は `design-check-report-〈対象〉.md`（例: `-top` / `-works-detail`）と対象別に分けて上書きしない（ラウンド管理が対象ごとに独立し、過去ラウンドの内容をgit履歴からしか掘れない状態を防ぐ）。

```markdown
# Design Check Report: 〈案件名〉 〈日付〉

## 監査情報
- 対象: 〈top / 下層テンプレート / ページ名〉
- ラウンド: n / 3
- 前回ERROR対応表（ラウンド2以降は必須。前回レポートのERRORを全件列挙する）
  | 前回の指摘 | 今回の状態（解消 / 残存 / 悪化） | 根拠 |
  |---|---|---|

## 総合判定: 🟢 合格 / 🟡 条件付き合格 / 🔴 要修正（ERROR n件 / WARN n件）

## STEP 1a: 静的チェック
| # | 項目 | 判定 | 根拠 |
|---|---|---|---|
| 1 | eyebrow過多 | OK | セクション8つ中2個（上限3個） |
| … | | ERROR | 〈ファイル:行〉 |

## STEP 1b: レンダリング実測
（同形式。実測値を必ず記載。実測できなかった項目は「未実測」と明記）

## STEP 2: 症状判定
| 症状 | 判定 | 該当箇所 |
|---|---|---|

## 要検証（較正前項目・判定保留）
（#34〜#44・STEP 1b #6/#7 のうち基準に触れたもの。**通常のWARNと混ぜない**。総合判定には数えない）
| # | 項目 | 観測値 | 表の基準 | このケースで基準は妥当か |
|---|---|---|---|---|
| 34 | 余白のスケール外直値 | 7件 | 5件以上でERROR | 〈妥当 / 厳しすぎ / 緩すぎ＋理由1行〉 |

## STEP 3: 人間確認へ引き継ぐ項目
（本スキル STEP 3 のリストを転記する。機械検証では実施せず「人間確認待ち」として残す——総合判定には数えない）
- [ ] 〈項目〉

## ERROR詳細
### ERROR-1: 〈項目〉 [重要度: 高/中/低]
- 期待: 〈design-brief または本スキルの基準〉
- 実際: 〈観測された現象。数値・箇所を具体的に〉
- 修正方針: 〈1行〉
```

- 判定ラベルは **OK / WARN / ERROR / 未検証** の4種＋較正前項目専用の **要検証**。較正前項目（#34〜#44・STEP 1b #6/#7）が基準に触れたら、STEP 1a/1b の表の判定欄には「要検証」とだけ書き、観測値と評価は「要検証」枠に書く（基準に触れていなければ通常どおり OK）。根拠は必ず数値で書く（「eyebrow 5個 / 上限3個」のように）
- 修正提案は design-taste のダイヤル値・パレットと矛盾しないこと
- 「たぶん大丈夫」と言わない。カウント・実測できなかった項目は「未検証」「未実測」と明示する
- **「検証できていない」を「問題なし」にも「WARN」にも丸めない。** 判定できなかった項目は 未検証 / 未実測、**較正前の基準に触れた項目は「要検証」枠**に分けて書く。3つを混ぜると、レポートが「本物の指摘」と「基準を疑うべき項目」の区別を失い、較正がいつまでも進まない
- 要検証枠に書いた項目は**総合判定に数えない**（🟢 を妨げない）。ただし毎ラウンド必ず残し、「このケースで基準は妥当か」欄を埋める。**この欄の蓄積が較正の材料**で、同じ項目が複数案件で「厳しすぎ」と評価されたら checks.md の較正手順に回す
