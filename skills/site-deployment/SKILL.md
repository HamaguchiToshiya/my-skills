# 本番公開・サーバー移行

静的サイト・WordPressサイトをレンタルサーバーに公開するまでの標準手順。ユーザーはエックスサーバー等の国内レンタルサーバーを使う想定だが、サーバー名が分かれば管理画面の名称に合わせて案内する。

公開作業は**やり直しが効きにくい**ため、必ず「事前準備 → 移行 → 切り替え → 確認」の順で進め、切り替え前にロールバック手段（バックアップ）を確保してから作業する。

## 0. 公開前の前提確認

作業に入る前に以下をユーザーに確認する（不明なら聞く）:

- [ ] 新規公開か、既存サイトのリニューアル（旧サイトあり）か
- [ ] ドメインは取得済みか・DNSはどこで管理しているか（サーバー会社 / お名前.com等の別会社）
- [ ] サーバーの契約者は自分かクライアントか（クライアント契約の場合、作業権限・アカウント共有方法を確認）
- [ ] pre-delivery-checklistのチェックが完了しているか
- [ ] メールをそのドメインで運用しているか（**DNS切り替えでメールが止まる事故が最頻出**。MXレコードの扱いを必ず確認）

## 1. 静的サイトの公開

### アップロード

- 基本はサーバーのファイルマネージャーまたはSFTP（FileZilla等）。FTP（非暗号化）は使わない
- アップ先はサーバーのドキュメントルート（エックスサーバーなら `/ドメイン名/public_html/`）
- `node_modules/`、`src/`（ビルド前ソース）、`.git/`、デザインデータは**アップしない**。ビルド成果物（`dist/` の中身等）のみ
- Git管理している案件では、git-workflowスキルのデプロイ準備（ビルド→成果物確認）を先に行う

### .htaccess の基本セット

新規公開時の標準形。コメントごと提示してよい:

```apache
# https・www無しに統一（301リダイレクト）
RewriteEngine On
RewriteCond %{HTTPS} off [OR]
RewriteCond %{HTTP_HOST} ^www\. [NC]
RewriteRule ^(.*)$ https://example.com/$1 [R=301,L]
```

- ドメイン部分は必ず案件の本番ドメインに置換する
- www有り統一にするかはクライアントの既存資産（被リンク・印刷物のURL表記）に合わせて確認
- リニューアル案件で**URL構造が変わる場合**は、旧URL→新URLの301リダイレクト対応表を作ってから `RedirectPermanent` または `RewriteRule` で個別に設定する（SEO資産の引き継ぎ）
- 開発中にBasic認証をかけていた場合、公開時に**認証記述の削除を忘れない**

### テスト公開（クライアント確認用のBasic認証）

公開前にテストサーバー・本番サーバー上でクライアント確認する場合は、Basic認証 + noindexで外部から見えない状態にする。

```apache
# .htaccess（テスト公開ディレクトリ直下）
AuthType Basic
AuthName "Restricted"
AuthUserFile /home/アカウント名/フルパス/.htpasswd  # 相対パス不可。サーバーのフルパスを確認して指定
Require valid-user
```

- `.htpasswd` はサーバーのツール（多くのレンタルサーバーは管理画面にアクセス制限機能あり）か `htpasswd` コマンドで生成する。**パスワードを平文で書かない**
- 併せて `<meta name="robots" content="noindex">`（またはWPの「インデックスを回避」設定）を入れる
- **公開時は「Basic認証の削除」と「noindexの解除」を必ずセットで行う**（片方だけ外す漏れが定番事故）

## 2. WordPressの本番移行

Local等のローカル環境から本番サーバーへの移行手順。wordpress-developmentスキルで開発した案件が対象で、**WP移行手順はこのスキルを正とする**（wordpress-development側には重複記載しない）。

### 手順A: プラグイン移行（推奨・小〜中規模）

1. ローカルで「All-in-One WP Migration」でエクスポート（.wpress）
2. 本番サーバーにWordPressを新規インストール（サーバーの簡単インストール機能でよい）
3. 本番に同プラグインを入れてインポート
4. **インポート直後にパーマリンク設定を保存し直す**（404対策・必須）
5. ログインユーザーがローカルのものに置き換わるので、ログイン情報を控えておく

無料版は容量制限（512MB前後）があるため、超える場合はメディアを除外してエクスポートし、`wp-content/uploads/` をSFTPで別途アップする。

### 手順B: 手動移行（大規模・プラグインが使えない場合）

1. `wp-content/`（テーマ・プラグイン・uploads）をSFTPでアップ
2. ローカルDBをエクスポート → 本番のphpMyAdminでインポート
3. URL置換はSQLの直接置換ではなく**Search-Replace-DB等のシリアライズ対応ツール**か WP-CLI の `wp search-replace` を使う（ACFの設定値はシリアライズされているため、単純置換すると壊れる）
4. `wp-config.php` のDB接続情報を本番用に書き換え

### 移行後の必須確認

- [ ] ACFフィールドが表示されているか（acf-json同期の確認）
- [ ] 「検索エンジンによるインデックスを回避」設定をOFFにしたか
- [ ] `WP_DEBUG` が false か
- [ ] お問い合わせフォームの送信テスト（本番のメール環境で通知が届くか）

## 3. ドメイン・DNS・SSL

### DNSレコードの基礎（触る前に把握する）

DNS作業で事故が起きるのはレコードの役割を混同した時。最低限この4つを区別する。

| レコード | 役割 | 事故ポイント |
|---|---|---|
| A / AAAA | ドメイン→サーバーIPの紐付け（Webの向き先） | ここだけ変えればWebは切り替わる |
| CNAME | 別名（`www` → 本体等） | Aと同居不可の制約あり |
| MX | **メールの配送先** | ネームサーバーごと変えるとWebと一緒にメールも移動してしまう |
| TXT（SPF/DKIM/DMARC） | 送信メールのなりすまし防止 | 未設定・移行漏れだとフォーム通知や自動返信が迷惑メール行き（form-implementationのメール到達性と直結） |

- 「ネームサーバー変更」は**全レコードを新環境の設定に丸ごと差し替える操作**。メール継続利用がある場合は、切り替え前に旧環境のMX/TXTを新環境のDNS設定に転記しておく
- Webだけ移したい（メールは現状維持）なら、ネームサーバーは変えずAレコードのみ変更する選択肢を先に検討する
- フォームのメール不達相談を受けた場合も、まず送信ドメインのSPF（TXT）設定を確認する

### 新規ドメインの場合

1. サーバーにドメインを追加設定
2. DNS（ネームサーバー）をサーバー指定のものに変更
3. 反映待ち（数分〜最大72時間。通常は1〜2時間程度）
4. 無料独自SSL（Let's Encrypt）を設定 → 反映後に .htaccess のhttpsリダイレクトを有効化

### リニューアル（サーバー移転を伴う）場合

DNS切り替え前に**hostsファイルで新サーバーの表示確認**を行うのが定石:

```
# hosts に追記して新サーバーを事前確認（作業後は必ず削除）
（新サーバーのIP） example.com
```

- 確認完了後にDNSを切り替える。切り替えは**平日午前など、問題発生時に対応できる時間帯**に行う
- 旧サーバーはすぐ解約せず、**最低1〜2週間は並行稼働**させる（DNS浸透中は旧サーバーにアクセスが流れるため）
- メールを使っている場合、MXレコードだけ旧環境を向け続ける必要がないか必ず確認する

## 4. 公開直後チェック

- [ ] シークレットウィンドウ＋スマホ実機（Wi-Fiオフのモバイル回線）で表示確認
- [ ] https強制・www統一リダイレクトが効いているか（http:// や www付きでアクセスして確認）
- [ ] フォーム送信の本番テスト
- [ ] Search Consoleにプロパティ登録し、sitemap.xmlを送信
- [ ] 旧URLからの301が意図通りか（リニューアル案件）
- [ ] SSL証明書が有効か（鍵マーク・証明書のドメイン名）
- [ ] Basic認証・noindexの解除漏れがないか

## 出力形式

- 手順を提示する場合は、その案件の構成（静的/WP、新規/リニューアル、サーバー名）に合わせて不要な項目を削って提示する
- コマンドや.htaccessを提示する際は、ユーザーが置換すべき箇所（ドメイン名等）を明示する
- 破壊的な操作（DNS切り替え、DB上書き、旧サーバー解約）の前には、必ずバックアップと戻し方をセットで案内する
