# 既存サイト改修

他人が書いたコードの改修は、新規制作と進め方が根本的に違う。**「自分の書き方」より「壊さないこと」を優先**し、調査 → 影響範囲の見極め → 最小限の変更、の順で進める。

## 0. 大原則

- **既存の命名規則・書き方に従う**。既存サイトがBEMでもオレオレ命名でも、改修部分だけFLOCSSにしない（coding-standardは新規制作用。混在は次の改修者を苦しめる）
- **リファクタリングと改修を混ぜない**。「ついでに綺麗にする」は影響範囲が読めなくなる最大の原因。リファクタが必要なら別作業として提案する
- 触る前に**現状のバックアップ**（ファイル一式＋WPならDB）。Git管理されていなければ、作業開始時点をコミットしてから始める（git-workflowスキル参照）
- 動いているコードには理由がある前提で読む。「なぜこう書いた？」と思っても、まず消さずに理由を探る

## 1. 着手前の調査

### 環境の把握

- [ ] Git管理されているか / されていなければローカルにコピーを取ってから作業
- [ ] ビルド環境の有無（Sass、bundler等）。**srcとdistのどちらを渡されたか**を必ず確認 — distだけ渡されてsrcが行方不明のケースが頻出。CSSがビルド成果物なのに直接編集すると、次のビルドで消える
- [ ] テスト環境があるか、本番直編集しかないか（本番直の場合は作業時間帯・バックアップを慎重に）
- [ ] WordPressの場合: テーマは自作かテーマ買い切りか、**子テーマ運用か親テーマ直編集か**、プラグイン一覧、WP/PHPバージョン

### コードの把握

- CSSの設計方針を推測する: 命名規則（BEM風？接頭辞？）、詳細度の傾向、`!important`の多用有無、メディアクエリの書き方（ブレークポイント値をメモ）
- JSの依存を確認: jQuery前提か、素のJSか、ライブラリのバージョン
- 共通パーツ（ヘッダー・フッター）の管理方法: 各HTMLにベタ書きか、インクルードか、JSで挿入か — ページ追加時の作業量が大きく変わる

## 2. 影響範囲の見極め

改修で壊すのは大抵「見えていない他のページ」。変更前に必ず確認する:

- **そのクラスは他のどこで使われているか**: エディタのプロジェクト全体検索（grep）でクラス名を検索してから触る。共通クラスへの変更は全使用箇所に影響する
- 共通CSSを変更する場合は、**新しいクラスを追加して該当箇所だけに当てる**方が安全（既存クラスの上書きより影響が読める）
- JSの関数・イベントも同様にgrepで使用箇所を確認。グローバル変数を書き換えていないか注意
- WordPressの場合: テンプレート階層を確認し、**その変更がどの投稿タイプ・どのページに効くか**を特定する（`single.php`の変更は全記事に効く）。プラグイン由来の出力かテーマ由来かの切り分けも先に行う

## 3. 変更の進め方

- 変更は**最小差分**で。1つの依頼に対して触るファイル・行数を最小にする
- 既存CSSと競合する場合、`!important`で殴らず、詳細度を1段だけ上げる（既存セレクタに1クラス足す等）か、対象を限定した新クラスで対応
- 追加するコードには自分の作業と分かるコメントを付ける（例: `/* 2026-07 ○○追加: キャンペーンバナー */`）。次の改修者（未来の自分含む）への引き継ぎになる
- ページ追加の場合: 既存ページを1枚コピーして雛形にし、head内のtitle/description/OGP・パンくず・アクティブ状態のナビを直す（seo-meta-implementationスキル参照）

## 4. 検証

- 変更箇所のページだけでなく、**同じ共通パーツ・共通クラスを使う代表ページを最低2〜3ページ**確認する
- 確認するブレークポイントは既存サイトの実装に合わせる（調査時にメモした値）
- WordPressはプレビュー/テスト環境で確認後に本番反映。キャッシュ系プラグインがある場合は**キャッシュクリアまでが反映作業**
- 改修前後のスクリーンショットを残す（クライアント報告用＋デグレード時の証跡）

## 5. クライアント・引き継ぎコミュニケーション

- 調査の結果、想定より複雑だった場合（ビルド環境喪失、コードの劣化が激しい等）は、**着手前に**追加工数か対応範囲の調整を相談する。黙って吸収しない
- 「直してほしい」と言われた箇所が既存の構造的問題に起因する場合、対症療法（今回の範囲）と根本対応（別途提案）を分けて提示する
- 触っていない箇所の既存不具合を発見したら、修正はせず報告に留める（勝手に直すと「あなたが触ったから壊れた」と言われるリスク）

## 出力形式

- コードを提示する際は、既存コードの書き方（命名・インデント・jQuery使用等）に合わせる。モダンな書き方への変更は、提案として分離して添える
- 変更diff（どのファイルのどこを変えるか）を明示し、影響範囲（このクラスは他に○ページで使用）を添える
- 調査が必要な場合は、ユーザーに何を貰えば調査できるか（該当ファイル、URL、スクリーンショット）を具体的に依頼する
