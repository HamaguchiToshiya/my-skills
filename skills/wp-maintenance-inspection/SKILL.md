# WordPress保守点検ルール

納品後のWordPressサイトを保守点検する際のルール。実装フェーズの`wordpress-development`とは別の、**運用フェーズ**を担当する。

## 保守点検の基本メニュー（月次点検の目安）

一人で複数サイトを保守する前提で、点検項目をチェックリスト化しておく。

1. **表示確認**: トップページ・主要下層ページがPC/SPで正常表示されるか目視確認
2. **WordPress本体・プラグイン・テーマの更新状況確認**: 更新がある場合、変更履歴（changelog）を確認してから適用するか判断する
3. **バックアップの取得確認**: 直近のバックアップが正常に取れているか（自動バックアップの場合は失敗通知が来ていないか）
4. **稼働確認**: サイトが落ちていないか（uptime監視ツールの通知有無、または手動アクセス確認）
5. **お問い合わせフォームの送信テスト**: 月1回など定期的に実際に送信して受信確認まで行う（フォームは気づかず壊れているケースが多い）
6. **エラーログの確認**: サーバーのエラーログ、WordPressのデバッグログに異常が出ていないか
7. **容量確認**: メディアライブラリ・DB容量がプランの上限に近づいていないか
8. **SSL証明書の有効期限確認**: 自動更新でない場合は特に注意

## トラブル対応フロー

### 画面が真っ白（White Screen of Death）になった場合

1. サーバーのエラーログ、または `wp-config.php` に `WP_DEBUG` を一時的に有効化してエラー内容を確認する
2. 直前に更新したプラグイン・テーマがないか確認する（更新直後のトラブルが最多）
3. 心当たりのあるプラグインをFTP/ファイルマネージャーから該当プラグインフォルダをリネームして無効化 → 復旧するか確認（管理画面に入れない場合の定番の切り分け方法）
4. 復旧したら、原因プラグインの代替を検討するか、開発元に問い合わせる

```php
// wp-config.php に一時的に追加してエラー内容を確認
define('WP_DEBUG', true);
define('WP_DEBUG_LOG', true);
define('WP_DEBUG_DISPLAY', false);
```
※ 確認後は必ず `WP_DEBUG` を `false` に戻す（本番でエラー表示を出しっぱなしにしない）

### レイアウトが崩れた場合

1. キャッシュの問題か切り分ける（ブラウザキャッシュのスーパーリロード、サーバー側/プラグイン側のキャッシュクリア）
2. 直前のプラグイン更新（特にページビルダー・キャッシュ系プラグイン）が原因でないか確認する
3. CSS/JSの読み込み順が変わっていないか（`functions.php`のenqueue部分）を確認する

### 表示が重い・遅いという相談を受けた場合

1. PageSpeed Insights等で計測し、数値（LCP/CLS/INP）で現状を把握する
2. 画像サイズが肥大化していないか（`coding-standard`の画像最適化の観点で確認。特に更新担当者が最適化前の画像をそのままアップロードしているケースが多い）
3. プラグインの入れすぎ・不要プラグインの放置がないか確認する
4. キャッシュ系プラグイン・画像遅延読み込みの導入状況を確認する

## バックアップ運用

- 自動バックアップ（プラグインまたはサーバー機能）を必ず設定し、**保存先はサーバー本体とは別の場所**（外部ストレージ、クラウド等）にする（サーバー障害時に巻き込まれないため）
- 頻度の目安: 更新頻度が高いサイト（ブログ等）は日次、更新頻度が低いサイト（コーポレートサイト）は週次でも可
- 「バックアップを取っている」だけでなく、**年に数回は実際に復元テストをする**ことを推奨する（復元できないバックアップは意味がないため）

## プラグイン・本体更新の進め方

- メジャーアップデート（WordPress本体のバージョンが大きく変わる等）は、まずステージング環境（本番と別の検証用環境）で確認してから本番に適用する
- ステージング環境がない小規模サイトの場合は、更新前に必ずバックアップを取ってから適用する
- 更新は「自動更新に任せきり」にせず、更新後に必ずサイトの表示確認を行う運用にする
- 開発が長期間止まっている（最終更新から2年以上等）プラグインは、脆弱性リスクとして代替を検討する候補にする
- **PHPバージョンの点検**: サーバーパネルで現行のPHPバージョンを確認し、公式サポートが終了（EOL）したバージョンなら移行を提案する。目安として2026年時点ではPHP 8.1以下がEOL済み（8.1は2025年12月末終了）、WordPress推奨は8.3以上、WordPress 7.0で最低要件が7.4に引き上げ。**EOL期限とWP推奨バージョンは毎年変わるため、点検時にWeb検索で最新状況を確認してから判断する**。移行時は互換性確認→（可能なら）ステージング検証→バックアップ→切替→直後のエラーログ監視、の順で進め、不具合時は原因調査より切り戻しを優先する

## セキュリティ基本対策

- ログインURL（`/wp-admin`等）の変更、またはログイン試行回数制限プラグインの導入でブルートフォース攻撃対策をする
- 管理者ユーザー名を `admin` のような推測されやすいものにしない
- 不要なプラグイン・テーマ（無効化しているだけのもの）は削除する（脆弱性の温床になるため）
- `wp-config.php`のセキュリティキー（`AUTH_KEY`等）を初期設定のままにしない
- REST APIやXML-RPCなど、使っていない機能は必要に応じて無効化を検討する

## 点検レポートのテンプレート

保守契約先への報告用に、以下の形式でまとめる。

```markdown
# ◯◯様サイト 月次保守点検レポート（2026年◯月）

## 点検結果サマリー
- 表示確認: 問題なし
- WordPress本体: v6.x（最新）
- プラグイン更新: ◯件（詳細は下記）
- バックアップ: 正常に取得済み（最終取得日: ◯月◯日）
- お問い合わせフォーム: 送信テスト済み・正常

## 更新した項目
- プラグイン名A: v1.2 → v1.3（不具合修正のため）

## 発見事項・ご提案
- （あれば記載。なければ「特筆事項なし」）

## 次回点検予定日
- 2026年◯月◯日
```

## 出力形式

- トラブル対応時は「切り分けの手順」を1つずつ順番に案内する（一度に全部提示せず、結果を見ながら次の手を出す）
- 定期点検時は上記テンプレートに沿ってレポートをMarkdownまたはWord文書として作成する
