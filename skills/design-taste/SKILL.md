# デザインテイスト標準（Design Read / テイストファミリー / アンチスロップ）

Web制作の実案件でビジュアルデザインを作る・評価する際は、常にこのスキルを判断基準として適用する。

## 位置づけと分担

本スキルは**ワイヤーフレーム確定後〜実装前の「ビジュアル判断層」**。情報設計は `wireframe-proposal`、実装ルールは `coding-standard`（正）、アニメーション実装は `animation-implementation`（正）に委譲する。本スキルはコードの書き方を規定しない。**何をどう見せるかの判断**だけを規定する。

| 工程 | 内容 | 参照先 |
|---|---|---|
| 設計 | 情報設計・ワイヤー | `wireframe-proposal` |
| **デザイン** | **方向性決定・ビジュアル判断・品質監査** | **本スキル（正）** |
| 実装 | デザイントークンのSCSS化・実装 | `coding-standard` |
| 実装 | モーション実装 | `animation-implementation` |
| 検証 | 実装後のAIスロップ検証 | `design-verification`（正） |
| 納品 | 最終チェック | `pre-delivery-checklist` |

マルチエージェント運用時：ディレクターエージェントは本スキルの Phase 1〜3 を使って `design-brief.md` を作成し、デザインエージェントは Phase 4〜6 に従って制作、確認エージェント（`design-checker`）は `design-verification` スキルに従って検証する。

## 基本原則

**LLMのデザインが弱い最大の原因は、ブリーフを読まずに学習データの平均的デザイン（＝デフォルト美学）へ飛びつくこと。** 本スキルの全ルールはこの一点を防ぐためにある。

1. **オーディエンスがテイストを決める。**自分の好みでも流行でもない
2. **すべての装飾に理由を言えること。**言えない装飾は削る
3. **判断は宣言してから。**コードやカンプより先に Design Read を書く

## Phase 1: Design Read（着手宣言）

デザイン作業に入る前に、必ず以下を1〜3行で宣言する。宣言なしでデザインを始めることを禁止する。

```
Design Read:
「〈ページ種別〉を〈オーディエンス〉向けに、〈トーン語彙〉の方向で作る。
テイストファミリーは〈ファミリー名〉、参考DNAは〈参考サイトの構造・色・タイポの要点〉」
```

宣言の材料のうち**オーディエンスとページ種別が不明な場合のみ**ヒアリングに差し戻す（`hearing-estimate` と連動）。参考サイトの欠如は差し戻し理由にしない（下記「おまかせの場合」で処理する）。

**曖昧点は作り始める前に潰す**：差し戻し対象でなくても、解釈が分かれる点・デザイン判断に効く未確定事項（素材の質、既存資産の扱い、NG事項など）が残っていれば、推測で走らず**曖昧点を箇条書きで列挙し、1項目ずつ答えられる形（はい/いいえ、または選択肢つき）でまとめて質問する**。回答を待てない項目は仮置きと明示して design-brief.md に残す。

**確認する材料：**
- ページ種別：コーポレート / LP / 採用 / 店舗・クリニック / ポートフォリオ / ECなど
- オーディエンス：発注担当者・BtoB / 一般消費者 / 求職者 / 採用担当者など。**オーディエンスの解像度がテイストの解像度**
- **意思決定者と利用者が別人の場合**（子ども向け教室と保護者、介護施設と家族、採用サイトと経営者など）：**意思決定者を主、利用者を従**とする。利用者の世界観は「見せ物」（ヒーロー・あしらい・キャラ）として使い、意思決定者が読む部分（料金・実績・説明）は主側のルールで作る。「カラフルに」等の要望は見せ物側で叶える
- クライアントの既存資産：ロゴ・ブランドカラー。**既存資産は出発点であって無視してよい素材ではない**
- **ビジュアル素材の質と種類**：プロ撮影 / 支給（素人撮影）/ ストック / イラスト・キャラクター / なし。**素材が弱い場合は写真依存度の低い構成（図版・アイコン・タイポ主体）に倒す**。この判断はファミリー選択より優先する。**イラスト・キャラ素材が支給される場合は、その色をスポイトしてパレットの供給源にする**（素材とUIのトーンが自動的に揃い、パレット発明の事故を防げる）
- 業種由来の制約：医療・金融・公共系は信頼が装飾に優先する。この制約はテイストの好みより強い

**リニューアル案件の場合（現状監査が先）**：
既存サイトがある案件では、Design Read の前に現行サイトを Phase 6 の6軸で採点し、**「残すもの / 捨てるもの」を宣言**してから進む。

- 残す候補：コンテンツ資産（製品情報・沿革・実績）、顧客が慣れた主要導線、SEOで機能しているページ構造
- 捨てる候補：装飾・レイアウト・古いトーン
- 全面リニューアル（デザイン一新）は本スキル、既存デザインを保ったままの部分改修は `existing-site-modification` が正。判断に迷ったら「既存の見た目を維持するか」で分ける

**参考サイトが未支給・「おまかせ」の場合**（Crowdworksで頻出）：
ヒアリングに差し戻して待つのではなく、ディレクター側が**方向性の異なる参考候補を2〜3件提案し、クライアントの承認を得てから**DNA抽出に進む。承認前に本デザインへ着手しない。「おまかせ」は白紙委任ではなく「候補を出す仕事の依頼」と読み替える。

**クライアントへの提示形式（提案1枚HTML）**：方向性の候補や複数デザイン案の比較をクライアントに見せる際は、調査結果・案の比較・推奨案と理由を1つのHTMLにまとめる（雛形と運用ルールは `wireframe-proposal` の「提案1枚HTML」節が正）。デザイン案の比較欄には Design Read・ダイヤル値・トレードオフを必ず記載する。合意された案の内容がそのまま design-brief.md の材料になる。

## Phase 2: 3つのダイヤル

Design Read の直後に、以下3値を 1〜10 で宣言する。この値がレイアウト・モーション・余白のすべての判断の根拠になる。エージェント間の受け渡し（PROMPT.md / design-brief.md）にはこの数値を必ず記載する。

| ダイヤル | 1 | 10 | 意味 |
|---|---|---|---|
| VARIANCE | 完全な整列・対称 | 崩し・重なり・回転あり | レイアウトの遊び度 |
| MOTION | 静的 | スクロール連動・演出多め | アニメーションの深度 |
| DENSITY | 余白たっぷり | 情報ぎっしり | 1画面あたりの情報量 |

**業種別の推奨レンジ（初期値の目安。クライアント要望が優先）：**

| 案件タイプ | VARIANCE | MOTION | DENSITY |
|---|---|---|---|
| 士業・医療・金融 | 2–3 | 2–3 | 4–5 |
| 一般コーポレート | 3–5 | 3–5 | 4–6 |
| 店舗・飲食・美容 | 4–6 | 4–6 | 3–5 |
| LP（商品訴求） | 4–6 | 5–7 | 5–7 |
| 採用サイト | 5–7 | 5–7 | 3–5 |
| クリエイティブ・ポートフォリオ | 6–9 | 6–9 | 2–4 |

**複合案件のルール**（例：整体院のLP＝店舗×医療×LP）：
案件が複数行に該当する場合は**ページ種別の行（LP・採用など）を基準**とする。ただし業種制約（医療・金融・公共）に該当する場合は、VARIANCE と MOTION の**上限をその業種の行の値まで切り下げる**。DENSITY はページ種別の値を維持してよい（情報量は信頼を毀損しないため）。

**表にない業種**（教室・スクール、NPO、士業以外の専門サービス等）は、「オーディエンスが最も近い行」で代用する（業種の見た目ではなく、**誰が読むか**で選ぶ）。代用した旨と根拠を design-brief.md に一言残す。

MOTION の値は `animation-implementation` に引き継ぐ（値→実装手段の対応表は同スキル「0. 着手前に確認すること」が正。ここに複製しない）。

## Phase 3: テイストファミリー選択

以下から1つを主軸として宣言する。**混ぜる場合は主従を決める**（例：「信頼系ベース＋ポップのアクセント」）。主従なしの折衷はぼやけたデザインの最大要因。

### A. ポップ・ビビッド（高彩度・遊びあり）
店舗・イベント・キッズ・エンタメ・個性重視の採用など。
- **高彩度は面積比で成立させる**：ベースは明度の高いニュートラル（白〜オフホワイト）または1色の淡色。高彩度色は見出し・ボタン・図形など面積の小さい要素に刻む。画面の7割を高彩度で塗ると安っぽくなる
- **トーンを揃える**：ビビッドならビビッドで統一。ビビッドとくすみパステルの混在は事故
- **形状言語を固定**：角丸大＋線太＋ベタ影（オフセットシャドウ）等、1セットに統一。要素ごとに角丸半径が変わるのは禁止
- **遊びの主役は1画面に1つ**：回転・重なり・手書き風などの「崩し」は視線の行き先を1つに絞る
- フォントはラウンド系・ファット系の見出し（M PLUS Rounded 1c、Zen Maru Gothic、Mochiy Pop等）＋読みやすい本文の組み合わせ

### B. 信頼・コーポレート
士業・医療・BtoB・金融。
- 彩度を抑えたブランドカラー1色＋ニュートラル。アクセントは最小限
- 整列・グリッドの正確さがそのまま信頼感になる。VARIANCE低め
- 写真の質がすべてを決める。素材が弱いなら図版・アイコン・タイポ主体に切り替える判断をする

### C. 上質・ミニマル
高価格帯サービス・建築・ブランドサイト。
- 余白が主役。DENSITY 2〜3
- 明朝系（Shippori Mincho、Zen Old Mincho、Noto Serif JP）の見出しが効く数少ない領域
- 装飾より字間・行間・写真トリミングの精度で勝負する

### D. ナチュラル・やさしい
クリニック・保育・食品・地域サービス。
- 低〜中彩度のアースカラー・くすみカラー。白背景に1〜2色
- 角丸中・細線・手書き風あしらいは少量なら可
- 「やさしい＝ぼんやり」ではない。コントラスト比は必ず確保する（Phase 5参照）

### E. クール・テック
IT・SaaS・スタートアップ。
- ダーク基調または白基調＋シャープな1アクセント
- **紫→ピンクのグラデーションヒーローは禁止**（AIスロップの代名詞）。グラデを使うなら同系色相内で
- 直線的・グリッド強め。数字・実績の見せ方が主役

> ファミリーの追加・調整は案件経験に応じて本スキルを更新する（skill auto-update パイプラインの対象）。

## Phase 3b: 参考DNAの抽出プロトコル

参考サイト（支給・提案承認のいずれも）からは、**サイト単位でなく要素単位**で抽出する。1サイトの丸ごと模倣・ピクセルコピーを禁止する。

**手順：**
1. **「どこが好きか」を先に確認する**。クライアントは大抵、参考ごとに参考にしたい要素が違う（例：A社は情報の信頼感、B社は見た目の洗練）。複数参考の方向性が矛盾して見えるのは、たいてい矛盾ではなく**要素の分担**
2. 各参考を4観点に分解して抽出する：
   - **構造**：セクションの並び・ヒーローの型・情報の階層
   - **配色のロジック**：具体的な色ではなく「1色＋ニュートラル」「面積比の付け方」等の考え方
   - **タイポ**：書体の系統・字間・見出しと本文のジャンプ率
   - **密度・余白**：1画面の情報量・セクション余白の取り方
3. 観点ごとに「どの参考に従うか」の主従を決め、design-brief.md に記載する

**優先順位の鉄則：既存ブランド資産 ＞ 参考サイトの色。** 参考から色そのものは借りない。借りてよいのは配色のロジックだけ（クライアントのロゴ・ブランドカラーが必ず勝つ）。

## Phase 4: 共通ハードルール（全ファミリー適用）

### 4-0. 視覚階層（すべての判断の土台）
- 階層は**サイズ・ウェイト・色コントラストの3レバー**で作る。サイズだけに頼ると全部が大きくなり、色だけに頼ると散らかる
- **主役を盛るより脇役を下げる**：目立たせたい要素を装飾するより、周囲の要素のコントラスト・ウェイト・サイズを落とす方が上品に効く
- ラベル・補足・日付は本文より小さく・薄く。ラベルが本文と同じ強度で並ぶと表組みくさくなる
- 迷ったらグレースケールで階層が成立するかを先に確認する（色は階層の最後のレバー。色を抜いて読み順が崩れる設計は色に依存しすぎ）

### 4-1. 色
- 色は必ずデザイントークンとして定義してから使う（実装時は `_variable.scss` に落ちる。`coding-standard` 参照）
- **面積比の原則**：ベース約70% / サブ約25% / アクセント約5%。ポップ系でもこの構造は崩さない（アクセントの「数」が増えるだけ）
- アクセント色の役割を固定する：「CTA＝この色」を決めたら全ページで統一。同じ役割に違う色を使わない
- 意図のないグラデーション背景の禁止。特に紫系グラデ＋白センタリング文字

### 4-2. タイポグラフィ（和文）
- **タイプスケールを数値で固定してから組む**（デザイン初手。design-brief.md に記載）：
  - 本文16pxを基準に、比率の乗算でサイズ列を生成する。比率の目安：**1.125〜1.2**＝情報量の多いEC・アプリ・落ち着いた読み物 / **1.25**＝標準（コーポレート全般）/ **1.333〜1.414**＝LP・ブランド・訴求強め
  - **セクション見出し（h2）は本文の2〜3倍**（16px本文なら SP 28〜32px → PC 40〜48px）。**h2をラベル型（15px前後＋letter-spacing大）で済ませない**——小さく保つのは kicker（見出し上の添え）だけで、「はっきりした見出し」は kicker と h2 の**落差（ジャンプ率）**で作る
  - ジャンプ率は印象のダイヤル：高い＝躍動的・若々しい（ポップ・採用向き）、低い＝落ち着き・高級（上質・ミニマル向き）。意図的に低くする場合も **h2は本文の1.5倍を下限**とし、design-brief.md に宣言する
  - スケールの生成手順・流体タイポ（clamp）の安全則は `references/visual-craft.md` を参照
- 本文の1行は**全角35〜42字**を上限に `max-width` で制御する（PCフル幅に本文を流さない。行間は下記）
- **見出しと本文で書体の役割を分ける**。Noto Sans JP 一本で見出しも本文も済ませるのは和文版「Inter症候群」＝テンプレ感の最大要因
- 和文は最大2書体＋欧文1書体まで（パフォーマンスと統一感の両面。サブセット化は `performance-optimization` 参照）
- 見出しの詰め：`font-feature-settings: "palt"` ＋ `letter-spacing` 0.02〜0.05em を起点に調整。本文はツメすぎない（0〜0.05em、行間1.7〜2.0）
- 日本語見出しの改行位置は成り行きに任せない：`<br>` のレスポンシブ制御や `text-wrap: balance` を検討（`text-wrap: balance` は主要ブラウザ対応済みだが、非対応環境では単に無視される安全なフォールバック）
- 欧文あしらい（英字ラベル）は使ってよいが、**全セクション同型（英字ラベル＋日本語見出し）の機械的反復は禁止**。3セクションに1回程度に間引くか、形を変える

### 4-3. レイアウト
- **全センタリング症候群の禁止**：見出しも本文もボタンも中央揃え、をセクション連打しない。左揃え基調に1〜2箇所だけセンターを混ぜる方が意図が出る
- **同一レイアウトファミリーは1ページ1回まで**：「画像左・テキスト右」を使ったら次は反転・full-bleed・カード等、構造を変える
- **3等分カード即決の禁止**：要素が3つあるからと反射的に3カラムカードにしない。リスト・タイムライン・大小差のあるグリッド等を先に検討する
- カードは階層表現が必要なときだけ。区切りは罫線・余白でも作れる（カード多用＝AIスロップの典型）
- 余白はスペーシングスケール（8pxベース: 8/16/24/32/48/64/96/128/160）から選ぶ。セクションごとに任意の値を発明しない。**余白のリズムの乱れは「なんか素人っぽい」の正体**
- **余白は3層で設計する**：要素内 ＜ グループ間 ＜ セクション間。関連の強いものを近く、弱いものを遠く（近接）。特に**見出しは直後の本文に近づけ、前の要素から離す**（等間隔に置くとどちらに付く見出しか読めなくなる）
- セクション上下余白の目安：**PC 80〜160px / SPはその半分程度（48〜80px）**。`clamp()` で流体化してよい。SPの左右パディングは**16〜24px**
- 迷ったら**まず広めに取り、詰める方向で調整する**（狭い初期値から広げる調整は必ず詰まったまま終わる）

### 4-3b. 複数ページサイトの一貫性（固定と可変の線引き）

「同一レイアウトファミリー1ページ1回」は**ページ内**のルール。複数ページ構成では以下で統一と変化のバランスを取る。

- **全ページで固定**：デザイントークン（色・角丸・影・余白スケール）、ヘッダー/フッター、下層共通ヒーロー（ページタイトル部）、見出しスタイル（h2/h3の装飾）、あしらいの語彙
- **ページごとに可変**：セクションの構造・並び、写真とテキストの比率、そのページの主役要素
- **下層ページは「型」を共有する**：コース案内・料金・会社概要のような下層を毎回ゼロからデザインしない。共通の下層テンプレート（ヒーロー＋コンテンツ幅＋見出しスタイル）を1つ設計し、中身の構造だけ変える。**型を破ってよいのはTOPだけ**。統一感と制作工数の両方に効く

### 4-4. 形状・あしらい
- 角丸半径・線幅・影のスタイルはトークン化して統一。ボタンは8px角丸、カードは16px、画像は4px…のようなバラつきを禁止
- 絵文字（✨🚀等）をアイコンの代用にしない。アイコンはウェイト・スタイルの揃った1ライブラリに統一
- あしらい（ドット・波線・図形）は「ブランドの語彙」として2〜3種に絞り、全ページで同じ語彙を使い回す
- **「それっぽさ」のための疑似情報を作らない**：連番ラベル（`01 ·`）、装飾ステータスドット、バージョン風表記（`BETA` `v1.2`）、divで組む偽プロダクトUI、実在しない撮影クレジット、実情報でないメタ装飾（時刻・天気ストリップ等）は禁止。装飾は実在する情報だけで組む（検出基準は `design-verification` STEP 1a #18〜21 が正）

### 4-5. モーション
- **理由を言えないアニメーションは付けない**。「全要素ふわっとフェードイン」は無意味な演出の典型
- モーションは視線誘導・状態変化の伝達・ブランド表現のいずれかに紐づける
- `prefers-reduced-motion` 対応は必須（実装は `animation-implementation` が正）

### 4-6. コピー・ダミーテキスト
- デザイン内の全テキストを最終確認する：「ここにテキストが入ります」等のダミー残存、汎用キャッチコピー（「あなたのビジネスを次のステージへ」的な内容ゼロ文）、存在しない実績数字の捏造を禁止
- 原稿が未支給の箇所は、それらしい文を捏造せず `【原稿待ち：◯◯の説明 約40字】` の形式で明示する

### 4-7. ファーストビューの型

テンプレヒーロー（中央寄せ見出し＋サブテキスト＋CTA＋背景グラデの4点セット）に無自覚に落ちないため、以下から**意図を持って型を選び、design-brief.md に型名を記載する**。

| 型 | 概要 | 向く案件 |
|---|---|---|
| 全面ビジュアル | 写真/動画を全面に敷きコピーを重ねる | ブランディング・店舗。**素材が強い場合のみ** |
| スプリット | 画面を左右（上下）分割しコピーと画像を分離 | コーポレート全般。写真とコピーの両立 |
| 大胆タイポ | 巨大な和文/欧文見出しが主役 | 採用・クリエイティブ・メッセージ主導 |
| イラスト・キャラクター | 中央または片側に大きくイラスト | やさしい系・キッズ・無形サービス |
| シェイプ・くり抜き | 図形マスクで写真を個性的に見せる | 素材が中程度でも個性を出したい場合 |
| スライドショー | 複数ビジュアルを順送り | 実績・商品が複数あり更新性が高い場合 |
| コラージュ・レイヤー | 複数要素の重なりで奥行きを作る | VARIANCE 6以上の遊びが許される案件 |

- 中央寄せ構成を使うなら「型として選んだ」と言えること。VARIANCE 5以上なら非対称構成を優先（`design-verification` STEP 2 と対応）
- **素材の質が型の選択肢を決める**（Phase 1 の素材判断が先）。弱い素材で全面ビジュアル型を選ばない

### 4-8. 写真・画像の扱い
- **写真の上の文字は可読性を担保してから置く**：暗色/ブランド色のオーバーレイ、写真側のコントラストを下げる、文字裏だけ帯・グラデーションを敷く、のいずれかを使う。生の写真に白文字を直置きしない
- 同一ページの写真はトーンを揃える（明度・彩度・色温度）。支給素材がバラつく場合は同じ補正・同じトリミング比率を一括でかける
- トリミング比率は2〜3種に固定してトークン扱いする（16:9 / 4:3 / 1:1 等）。カードごとに比率が揺れるのは角丸の揺れと同じ事故
- スクリーンショット・ロゴを縮小して精細さが失われた状態で置かない（部分拡大に切り替えるか置かない）

---

## Phase 5: アクセシビリティの下限（デザイン段階で担保）

実装時でなく**デザイン判断の段階**で以下を守る。後から直すと配色が崩壊するため。

- 本文テキストのコントラスト比 4.5:1 以上、大きい文字（24px〜/太字19px〜）は 3:1 以上
- 色だけで意味を伝えない（エラー＝赤だけ、ではなくアイコン・文言を併用）
- ポップ系・ナチュラル系で淡い色を使う際が最も事故りやすい。**淡色背景×白文字は原則禁止**

---

## Phase 6: 出力前の自己採点

デザイン（カンプ・実装済みページ）を提出する前に、以下6軸を1〜5で自己採点する。**3未満が1つでもあれば提出せずリビジョン**。採点結果はコメントとして成果物に残す。

| 軸 | 問い |
|---|---|
| 方向性 | Design Read の宣言と成果物が一致しているか |
| 視線誘導 | 各画面で「最初に見る場所→次」の順路が設計されているか |
| 仕上げ | 余白のリズム・整列・トークン統一が守られているか |
| 具体性 | この業種・このクライアント固有の要素があるか（他社名に差し替えても成立するデザインは失格） |
| 抑制 | 削れる装飾を削ったか。全部盛りになっていないか |
| 構造 | 前回の案件・前のセクションと同じ構造の反復になっていないか |

## Phase 7: 実装後の検証（design-verification が正）

実装済みページの検証基準・チェック項目は `design-verification` スキルを正とする（静的チェック・レンダリング実測・症状判定の全リストと運用ルールはそちらに集約）。提出前のセルフチェックも design-verification の STEP 1 を使う。

本スキルの宣言（ダイヤル値・テイストファミリー・トークン・禁止事項）が検証の入力になるため、**design-brief.md を必ず残す**こと。

## パイプライン連携: design-brief.md 雛形

ディレクターエージェント→デザインエージェントの受け渡しは以下の形式で行う。

```markdown
# Design Brief: 〈案件名〉

## Design Read
〈ページ種別〉を〈オーディエンス〉向けに、〈トーン語彙〉の方向で作る。

## ダイヤル
VARIANCE: n / MOTION: n / DENSITY: n

## テイストファミリー
主軸: 〈A〜E〉（従: あれば）

## 参考DNA（Phase 3b の4観点で要素単位に分解。ピクセルコピー禁止）
- 構造: 〈どの参考に従うか＋要点〉
- 配色ロジック: 〈色そのものは借りない。既存ブランド資産が優先〉
- タイポ: 〈例: ファット系見出し＋ゴシック本文〉
- 密度・余白: 〈例: 余白広め、1画面1メッセージ〉

## デザイントークン初期値
- 色: --color-base / --color-main / --color-accent1 ...
- タイプスケール: 本文16px × 比率1.25（h2: SP32px → PC48px 等、主要段を明記）
- 角丸: --radius-s/m/l　- 影: --shadow-…　- 余白スケール: 8px基準

## ファーストビューの型
〈4-7の表から選択。例: スプリット（写真右・コピー左）〉

## 禁止事項（この案件固有）
- 〈例: 競合◯◯社に似せない / 赤系は使わない〉

## 原稿状況
- 支給済み: 〈〉 / 原稿待ち: 〈〉
```
