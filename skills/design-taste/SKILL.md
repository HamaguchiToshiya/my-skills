# デザインテイスト標準（Design Read / テイストファミリー / アンチスロップ）

Web制作の実案件でビジュアルデザインを作る・評価する際は、常にこのスキルを判断基準として適用する。

## 位置づけと分担

本スキルは**ワイヤーフレーム確定後〜実装前の「ビジュアル判断層」**。情報設計は `wireframe-proposal`、実装ルールは `coding-standard`（正）、アニメーション実装は `animation-implementation`（正）に委譲する。本スキルはコードの書き方を規定しない。**何をどう見せるかの判断**だけを規定する。

| 工程 | 内容 | 参照先 |
|---|---|---|
| 設計 | 情報設計・ワイヤー | `wireframe-proposal` |
| **デザイン** | **方向性決定・ビジュアル判断** | **本スキル（正）** |
| 実装 | デザイントークンのSCSS化・実装 | `coding-standard` |
| 実装 | モーション実装 | `animation-implementation` |
| 検証 | 実装後のAIスロップ検証 | `design-verification`（正） |
| 納品 | 最終チェック | `pre-delivery-checklist` |

マルチエージェント運用時：ディレクター（本体）は本スキルの Phase 1〜3b を使って `design-brief.md` を作成し、Phase 3c（FVコンペ）では `designer` をFVコンペモードで起動して3案を制作させ、本体が選択・確定する。以降、デザイン制作エージェント（`designer`）は Phase 4〜7 に従って制作（Phase 7 のセルフ検証まで）、確認エージェント（`design-checker`）は `design-verification` スキルに従って検証する。ブリーフ作成はクライアント確認の対話が必要なためエージェント化しない（本体が担当）。

外部スキル `apple-design`（材料・タイポ・設計原則などデザイン部分を含む）はテイスト検討の参考リファレンスとして使ってよいが、**Phase 4 のハードルール・トークン制と矛盾する場合は本スキルが正**（外部スキル群の交通整理は `animation-implementation` の外部スキル節が正）。

## 基本原則

**LLMのデザインが弱い最大の原因は、ブリーフを読まずに学習データの平均的デザイン（＝デフォルト美学）へ飛びつくこと。** 本スキルの全ルールはこの一点を防ぐためにある。

現在のAI生成デザインは、題材を問わず次の**収束3パターン**のどれかに落ちる傾向が強い。ブリーフがこの方向を明示的に指定した場合は従ってよいが、ブリーフが自由に任せた軸をこの3型で埋めたら、それは選択ではなくデフォルトへの退行とみなす：

1. **クリーム地×セリフ×テラコッタ**：温かみのあるクリーム背景（#F4F1EA近辺）＋高コントラストのセリフ見出し＋テラコッタ系アクセント
2. **黒地×単色ネオン**：ほぼ黒の背景＋アシッドグリーンまたは朱色の単色アクセント
3. **新聞風ブロードシート**：ヘアライン罫＋角丸ゼロ＋新聞的な高密度カラム

この前提の上で、原則は3つ：

1. **オーディエンスがテイストを決める。**自分の好みでも流行でもない
2. **すべての装飾に理由を言えること。**言えない装飾は削る
3. **判断は宣言してから。**コードやカンプより先に Design Read を書く

## Phase 1: Design Read（着手宣言）

デザイン作業に入る前に、必ず以下を1〜3行で宣言する。宣言なしでデザインを始めることを禁止する。

```
Design Read:
「〈ページ種別〉を〈オーディエンス〉向けに、〈トーン語彙〉の方向で作る。
テイストファミリーは〈ファミリー名〉、参考DNAは〈参考サイトの構造・色・タイポの要点〉」
```

宣言の材料のうち**オーディエンスとページ種別が不明な場合のみ**ヒアリングに差し戻す（`hearing-estimate` と連動）。参考サイトの欠如は差し戻し理由にしない（下記「おまかせの場合」で処理する）。

**曖昧点は作り始める前に潰す**：差し戻し対象でなくても、解釈が分かれる点・デザイン判断に効く未確定事項（素材の質、既存資産の扱い、NG事項など）が残っていれば、推測で走らず**曖昧点を箇条書きで列挙し、1項目ずつ答えられる形（はい/いいえ、または選択肢つき）でまとめて質問する**。回答を待てない項目は仮置きと明示して design-brief.md に残す。（質問プロトコルの型は `wireframe-proposal` の「曖昧点は作り始める前に潰す」が正）

**参考リサーチのゲート（design-researcher 連動）**：Phase 1 開始時に design-research-report.md が存在するか確認する。無ければ、Design Read の材料（ページ種別・オーディエンス・トーン語彙）が固まった時点で調査指示をユーザーに確認し、`design-researcher` をバックグラウンド起動する（通常は hearing-import 完了時に起動済みのため、これはすり抜けた案件の保険。二重調査はしない）。Phase 1〜3b の対話と並走させ、レポートは Phase 3b の参考DNA、および「おまかせ」時の候補提案（2〜3件はレポートのサイトカードから選ぶ）の材料にする。既にレポートがある場合・クライアント支給の参考サイトで十分な場合・ユーザーが「調査スキップ」と言った場合は起動しない。

**確認する材料：**

（`hearing-import` 実行済みの案件では、先に `docs/hearing-notes.md` の「design-taste用材料」を読む——ページ種別・既存資産・雰囲気・参考サイトが整理済み。以下はその確認と補完）

- ページ種別：コーポレート / LP / 採用 / 店舗・クリニック / ポートフォリオ / ECなど
- オーディエンス：発注担当者・BtoB / 一般消費者 / 求職者 / 採用担当者など。**オーディエンスの解像度がテイストの解像度**
- **意思決定者と利用者が別人の場合**（子ども向け教室と保護者、介護施設と家族、採用サイトと経営者など）：**意思決定者を主、利用者を従**とする。利用者の世界観は「見せ物」（ヒーロー・あしらい・キャラ）として使い、意思決定者が読む部分（料金・実績・説明）は主側のルールで作る。「カラフルに」等の要望は見せ物側で叶える
- クライアントの既存資産：ロゴ・ブランドカラー。**既存資産は出発点であって無視してよい素材ではない**
- **ビジュアル素材の質と種類**：プロ撮影 / 支給（素人撮影）/ ストック / イラスト・キャラクター / なし。**素材が弱い場合は写真依存度の低い構成（図版・アイコン・タイポ主体）に倒す**。この判断はファミリー選択より優先する。**イラスト・キャラ素材が支給される場合は、その色をスポイトしてパレットの供給源にする**（素材とUIのトーンが自動的に揃い、パレット発明の事故を防げる）
- 業種由来の制約：医療・金融・公共系は信頼が装飾に優先する。この制約はテイストの好みより強い

**案件の状況による分岐**：

- **リニューアル案件（現状監査が先）**：既存サイトがある案件では、Design Read の前に現行サイトを Phase 6 の6軸で採点し、**「残すもの / 捨てるもの」を宣言**してから進む。残す候補＝コンテンツ資産（製品情報・沿革・実績）・顧客が慣れた主要導線・SEOで機能しているページ構造。捨てる候補＝装飾・レイアウト・古いトーン。全面リニューアル（デザイン一新）は本スキル、既存デザインを保ったままの部分改修は `existing-site-modification` が正（判断に迷ったら「既存の見た目を維持するか」で分ける）
- **参考サイトが未支給・「おまかせ」**（Crowdworksで頻出）：ヒアリングに差し戻して待つのではなく、ディレクター側が**方向性の異なる参考候補を2〜3件提案し、クライアントの承認を得てから**DNA抽出に進む。承認前に本デザインへ着手しない。「おまかせ」は白紙委任ではなく「候補を出す仕事の依頼」と読み替える
- **クライアントへの提示形式（提案1枚HTML）**：方向性の候補や複数デザイン案の比較をクライアントに見せる際は、調査結果・案の比較・推奨案と理由を1つのHTMLにまとめる（雛形と運用ルールは `wireframe-proposal` の「提案1枚HTML」節が正）。デザイン案の比較欄には Design Read・ダイヤル値・トレードオフを必ず記載する。合意された案の内容がそのまま design-brief.md の材料になる

## Phase 2: 3つのダイヤル

Design Read の直後に、以下3値を 1〜10 で宣言する。この値がレイアウト・モーション・余白のすべての判断の根拠になる。エージェント間の受け渡し（PROMPT.md / design-brief.md）にはこの数値を必ず記載する。

| ダイヤル | 1 | 10 | 意味 |
|---|---|---|---|
| VARIANCE | 完全な整列・対称 | 崩し・重なり・回転あり | レイアウトの遊び度 |
| MOTION | 静的 | スクロール連動・演出多め | アニメーションの深度 |
| DENSITY | 余白たっぷり | 情報ぎっしり | 1画面あたりの情報量 |

**業種別の推奨レンジ（初期値の目安。クライアント要望が優先）：**

| 案件タイプ | VARIANCE | MOTION | DENSITY |
|---|---|---|---|
| 士業・医療・金融 | 2–3 | 2–3 | 4–5 |
| 一般コーポレート | 3–5 | 3–5 | 4–6 |
| 店舗・飲食・美容 | 4–6 | 4–6 | 3–5 |
| LP（商品訴求） | 4–6 | 5–7 | 5–7 |
| 採用サイト | 5–7 | 5–7 | 3–5 |
| クリエイティブ・ポートフォリオ | 6–9 | 6–9 | 2–4 |

**複合案件のルール**（例：整体院のLP＝店舗×医療×LP）：
案件が複数行に該当する場合は**ページ種別の行（LP・採用など）を基準**とする。ただし業種制約（医療・金融・公共）に該当する場合は、VARIANCE と MOTION の**上限をその業種の行の値まで切り下げる**。DENSITY はページ種別の値を維持してよい（情報量は信頼を毀損しないため）。

**表にない業種**（教室・スクール、NPO、士業以外の専門サービス等）は、「オーディエンスが最も近い行」で代用する（業種の見た目ではなく、**誰が読むか**で選ぶ）。代用した旨と根拠を design-brief.md に一言残す。

**テイストファミリーの推奨値と衝突する場合**（例：一般コーポレート DENSITY 4–6 × ファミリーC「上質・ミニマル」DENSITY 2〜3）：ファミリーの選択は意図を持った判断なので**ファミリー側の値を優先**し、業種レンジから外れた旨とその理由を design-brief.md に宣言する（宣言なしで業種レンジを外れるのは禁止）。

MOTION の値は `animation-implementation` に引き継ぐ（値→実装手段の対応表は同スキル「0. 着手前に確認すること」が正。ここに複製しない）。

## Phase 3: テイストファミリー選択

以下から1つを主軸として宣言する。**混ぜる場合は主従を決める**（例：「信頼系ベース＋ポップのアクセント」）。主従なしの折衷はぼやけたデザインの最大要因。

5ファミリーの要約（**選定・適用時は必ず `references/taste-families.md` を読む**。各ファミリーの具体ルール・「LLMに渡すときの固有名」の渡し方と離し方の注意はそちらが実体）：

- **A. ポップ・ビビッド**（高彩度・遊びあり）：店舗・イベント・キッズ・エンタメ・個性重視の採用。高彩度は面積比で刻み、形状言語を1セットに固定（固有名: Material Design）
- **B. 信頼・コーポレート**：士業・医療・BtoB・金融。抑えたブランドカラー1色＋ニュートラル、整列・グリッドの正確さが信頼感（固有名: Swiss Design）
- **C. 上質・ミニマル**：高価格帯・建築・ブランド。余白が主役（DENSITY 2〜3）、明朝見出しが効く数少ない領域（固有名: Apple HIG系ミニマル / Editorial Design）
- **D. ナチュラル・やさしい**：クリニック・保育・食品・地域サービス。低〜中彩度のアースカラー・くすみ色、コントラスト比は必ず確保（固有名: Scandinavian Design）
- **E. クール・テック**：IT・SaaS・スタートアップ。ダークor白基調＋シャープな1アクセント。紫→ピンクのグラデーションヒーロー禁止（固有名: Fluent Design / Apple HIG系ミニマル）

designer・AIへ実装を渡すときは、ファミリー名に**LLMが既に知っている固有スタイル名を1語**添える（「おしゃれにして」系の抽象指示はスロップに落ちる）。ただし固有名は既製品の顔を呼ぶので骨格だけ借り、色とタイポで必ず離す——詳細は上記 references が正。

## Phase 3b: 参考DNAの抽出プロトコル

参考サイト（支給・提案承認のいずれも）からは、**サイト単位でなく要素単位**で抽出する。1サイトの丸ごと模倣・ピクセルコピーを禁止する。

**手順：**
1. **「どこが好きか」を先に確認する**。クライアントは大抵、参考ごとに参考にしたい要素が違う（例：A社は情報の信頼感、B社は見た目の洗練）。複数参考の方向性が矛盾して見えるのは、たいてい矛盾ではなく**要素の分担**
2. 各参考を4観点に分解して抽出する：
   - **構造**：セクションの並び・ヒーローの型・情報の階層
   - **配色のロジック**：具体的な色ではなく「1色＋ニュートラル」「面積比の付け方」等の考え方
   - **タイポ**：書体の系統・字間・見出しと本文のジャンプ率
   - **密度・余白**：1画面の情報量・セクション余白の取り方
3. 観点ごとに「どの参考に従うか」の主従を決め、design-brief.md に記載する

**優先順位の鉄則：既存ブランド資産 ＞ 参考サイトの色。** 参考から色そのものは借りない。借りてよいのは配色のロジックだけ（クライアントのロゴ・ブランドカラーが必ず勝つ）。

**参考スクショの受け渡し（ビジュアルアンカー）**：`design-researcher` がスクショを保存している場合（`design-research-assets/`）、その所在を design-brief.md に記載して designer に渡し、制作時に**テキスト要約だけでなくスクショを直接見て**判断させる。デザインをテキストだけで説明できるという誤解が平均への回帰（収束3パターン）を招く——共通認識は必ずビジュアルとセットで作る。スクショ参照時もピクセルコピー禁止・色は借りない、の鉄則は同じ。

## Phase 3c: FVコンペ（3案並列→選択ゲート）

design-brief.md 確定後、**全ページを1案で作り切る前に、ファーストビューだけを方向性の違う3案**作り、スクリーンショットを並べてユーザー（必要ならクライアント）に選んでもらう。言葉で詰めにくい「納得感」は、仕様の精緻化ではなく**選択肢の提示**で取りにいく。

**運用（マルチエージェント時）**：本体が `designer` を**FVコンペモード**で起動 → designer が3案＋スクショを納品 → 本体がスクショを並べて提示 → 選択とコメントを design-brief.md の「FVコンペ結果」に記録 → designer を新規制作モードで起動（選択案を正として全体展開）。

**3案の作り方**：
- **ブリーフが決めたことは3案共通**（ブランドカラー・テイストファミリー・ダイヤル値・禁止事項）。変えてよいのは**ブリーフが自由に残した軸**——FVの型（4-7）またはその執行（構図の崩し方・タイポの効かせ方・あしらいの語彙・写真の見せ方）
- 「安全寄り / 中庸 / 攻め」の一次元グラデーションにしない。**同じ強度で方向の違う別解**を出す（強弱の一次元だと結局中庸が選ばれ、選択から得られる情報が増えない）
- 各案に**1行の意図**（何を狙った案か）を付ける
- FVのみ・静的（モーションなし）・SP/PC両方。トークンは共通の変数ファイルを使い、案ごとの差分は最小のオーバーライドで持つ（選択後の展開コストを抑える）

**スキップ条件**：デザインカンプ支給案件（見た目の正が既にある）／参考サイトが1つに固定され方向の自由度が無い場合／小規模改修。スキップしたら design-brief.md の「FVコンペ結果」欄に理由を1行残す。

**選択後**：選ばれなかった案は削除せず `fv-comp/` に残す（提示履歴・後工程での部分流用のため）。「構図はAで色使いはBに寄せる」のような合成コメントはブリーフに追記し、以後の制作判断はブリーフが正。

## Phase 4: 共通ハードルール（全ファミリー適用）

**Phase 4 実施時（デザイン判断・トークン定義・カンプ/実装の作成時）は、必ず `references/phase4-hard-rules.md` を読む。** ルール・数値の実体はそちらが正で、以下は節の索引。`references/visual-craft.md` の同期表が design-taste 側として指す節番号（4-0〜4-8）も同ファイルの節を指す。

| 節 | 1行要約 |
|---|---|
| 4-0. 視覚階層 | 階層はサイズ・ウェイト・色コントラストの3レバーで作る。主役を盛るより脇役を下げる |
| 4-1. 色 | トークン定義が先。面積比 ベース70/サブ25/アクセント5、純グレー・純黒の禁止、ダーク面の階層は影でなく明度 |
| 4-2. タイポグラフィ（和文） | タイプスケールを数値で固定（h2は本文の2〜3倍・下限1.5倍）。スケール外直値・見出しitalic禁止、本文行長は全角35〜42字 |
| 4-3. レイアウト | 全センタリング症候群・3等分カード即決・カードinカードの禁止。余白は8pxスケールから3層で設計 |
| 4-3b. 複数ページの一貫性 | トークン・共通部・下層の型は全ページ固定、セクション構造は可変。型を破ってよいのはTOPだけ |
| 4-4. 形状・あしらい | 角丸・影・線幅をトークン統一。あしらい語彙は2〜3種。疑似情報（連番・BETA・偽UI等）の禁止 |
| 4-5. モーション | 理由を言えないアニメーション禁止。hover scale の横断適用禁止、prefers-reduced-motion 必須 |
| 4-6. コピー・ダミーテキスト | ダミー残存・汎用キャッチ・実績捏造の禁止。未支給箇所は `【原稿待ち：…】` 形式で明示 |
| 4-7. ファーストビューの型 | 7型（全面ビジュアル/スプリット/大胆タイポ/イラスト/シェイプ/スライドショー/コラージュ）から意図を持って選び design-brief.md に型名を記載 |
| 4-8. 写真・画像の扱い | 写真上の文字は可読性担保が先。同一ページのトーン統一、トリミング比率は2〜3種に固定 |

---

## Phase 5: アクセシビリティの下限（デザイン段階で担保）

実装時でなく**デザイン判断の段階**で以下を守る。後から直すと配色が崩壊するため。

- 本文テキストのコントラスト比 4.5:1 以上、大きい文字（24px〜/太字19px〜）は 3:1 以上
- 色だけで意味を伝えない（エラー＝赤だけ、ではなくアイコン・文言を併用）
- ポップ系・ナチュラル系で淡い色を使う際が最も事故りやすい。**淡色背景×白文字は原則禁止**

---

## Phase 6: 出力前の自己採点

デザイン（カンプ・実装済みページ）を提出する前に、以下6軸を1〜5で自己採点する。**3未満が1つでもあれば提出せずリビジョン**。採点結果はコメントとして成果物に残す。

| 軸 | 問い |
|---|---|
| 方向性 | Design Read の宣言と成果物が一致しているか |
| 視線誘導 | 各画面で「最初に見る場所→次」の順路が設計されているか |
| 仕上げ | 余白のリズム・整列・トークン統一が守られているか |
| 具体性 | この業種・このクライアント固有の要素があるか（他社名に差し替えても成立するデザインは失格） |
| 抑制 | 削れる装飾を削ったか。全部盛りになっていないか |
| 構造 | 前回の案件・前のセクションと同じ構造の反復になっていないか |

## Phase 7: 実装後の検証（design-verification が正）

実装済みページの検証基準・チェック項目は `design-verification` スキルを正とする（静的チェック・レンダリング実測・症状判定の全リストと運用ルールはそちらに集約）。提出前のセルフチェックは **design-verification STEP 1a（機械チェック）→ Phase 6（自己採点）の順で両方**行う——機械的な欠陥を先に潰してから、判断の質を採点する（どちらか片方では提出不可）。

本スキルの宣言（ダイヤル値・テイストファミリー・トークン・禁止事項）が検証の入力になるため、**design-brief.md を必ず残す**こと。

**brief確定後の案内（必ず一度は口に出す）**: design-brief.md が確定したら、カンプ作成・designer への受け渡しに進む前に、**参考イメージ生成（ChatGPT）の工程をユーザーに案内する**。手順・用途の使い分け（A: 方向性合意用 / B: カンプ代替）・brief→画像プロンプト変換の型は**テンプレの作業手順書 Phase 0.5 が正**。生成イメージはダイヤル値・禁止事項との brief 照合を通してから使う（無検証で正に昇格させない）。使わない判断も可だが、案内せずに素通りしない——この工程は案件側ファイルに発火点が無く、スキルのこの行だけが既存案件への到達経路。

**数値の同期**：本スキル Phase 4（本文は `references/phase4-hard-rules.md`）〜Phase 5 の数値・禁止事項の多くは design-verification STEP 1a の検出項目と対（作る基準⇔検証基準）で同じ値を持つ。対応の一覧は `references/visual-craft.md` の「design-verification との数値同期表」が索引。**どちらかの数値を改訂するときは、必ず同期表を辿って両側を同時に更新する**（片方だけ変えると、作った通りに実装したものが検証で落ちる）。
